# M2a-1 — REST API core & Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A versioned JSON API under `/api/v1` (OpenAPI 3.1 from code, RFC 9457 problems, cursors, `If-Match`) with real authentication (argon2id passwords, DB sessions with CSRF, scoped API tokens, DB-backed rate limits, TOTP), roles and token scopes enforced in core, user management (API + `ferrite user` CLI), the content, revision, type, taxonomy, term, menu, redirect and settings endpoints the admin needs, previews over HTTP and logged-in cache handling — on both backends, across nodes.

**Architecture:** One new expand migration `0005_auth` (sessions, API tokens, rate-limit windows, audit log, TOTP replay column) with repos and contract tests on both backends. `ferrite-core` gains token scopes on `Actor`, `auth` (site key, sealing, password hashing, `AuthService`), `users` (`UserService`), `types` (`ContentTypeService`, field schemas), `settings` (allowlist + validators) and admin read paths on `ContentService`. `ferrite-http` gains `src/api/` (utoipa-axum router, problem mapping, extractors, auth, one module per resource) merged with the public site by `build_site`; the public handler learns previews and logged-in requests. The binary loads the site key, wires the API into `serve`, adds `ferrite user …`, and `ferrite-cluster` gets the `sessions.prune` job. M2 is split three ways (P1): this plan is **M2a-1**; **M2a-2** (extensions, plugin API extras, media, comments, system endpoints, hardening, remaining deferred items) is outlined at the end and gets its own full plan; **M2b** is the admin SPA.

**Tech Stack:** axum 0.8.9, utoipa 6.0.0 + utoipa-axum 0.3.0 (new), argon2 0.6.0, totp-rs 6.0.0, hmac 0.13.0, chacha20poly1305 0.11.0, getrandom 0.4.3 (new), sha2 0.11 / base64 0.23 (existing), sqlx 0.9, tokio.

**Spec:** `docs/design/07-admin-api.md` §1–§2 (primary), `docs/design/04-cluster.md` §5–§6 (sessions, jobs), `docs/design/02-storage.md` §3–§4, §7–§8 (repos, auth tables, migrations), `docs/design/01-architecture.md` §4, §5, §8, `docs/design/05-plugin-host.md` §7a (preview scoping), `docs/design/06-themes-rendering.md` §6, `docs/design/09-operations.md` §8, `docs/design/10-testing.md`; ROADMAP M2 (backend items) and the M1a store item on e-mail case folding. ## Review Focus

1. **A cross-site form or script cannot act with an admin's cookie.** A cookie-authenticated `POST`/`PATCH`/`DELETE` without a valid `X-CSRF-Token`, or with an `Origin` (or, without `Origin`, a `Referer`) that is not the site's origin, must be `403` with nothing written — login included (login CSRF). Bearer requests are exempt. *Tests in Task 7 (`csrf_required_for_cookie_mutations`, `foreign_origin_is_refused`, `login_checks_origin`).*
2. **A stale editor tab cannot overwrite a newer save.** `PATCH`/`DELETE`/lifecycle `POST` on content with an old `If-Match` → `412` with the current resource in `current`; without `If-Match` → `428`; nothing written. *Tests in Task 8 (`stale_if_match_is_412_with_current`, `missing_if_match_is_428`).*
3. **Revoking access works at once on every node.** After a password change, role change, disable or delete, the user's old session and (for disable/delete) tokens are rejected on the next request on any node (no per-node session cache). *Tests in Task 5 (`revocation_is_immediate_on_peer`) and Task 11 (`role_change_logs_the_user_out`).*
4. **Brute force is throttled cluster-wide.** The 11th login attempt from one IP within a minute is `429` with `Retry-After`, also when the attempts alternate between two nodes on one database; the right password does not get through while limited. *Tests in Task 5 (`login_rate_limit_spans_nodes`) and Task 7 (`login_429_has_retry_after`).*
5. **A narrow token cannot do more than its scopes, whatever its owner's role.** An admin's `content:read` token can list drafts but gets `403` on create/publish/settings; a contributor's full-scope token still cannot publish. *Tests in Task 4 (`scopes_narrow_capabilities`) and Task 8 (`token_scope_limits_writes`).*

## Plan rulings

- **P1 — M2 is split three ways.** M2a-1 (this plan: auth, API core, users, content/types/terms/menus/redirects/settings endpoints, previews, logged-in bypass; 14 tasks), M2a-2 (extensions, plugin API extras, media, comments, system endpoints, hardening, the remaining deferred items; outlined below, its own plan), M2b (admin SPA, screens, Playwright E2E, embedded admin assets). One backend plan would be ~28 tasks, well past the ~16-task guide; auth and the API conventions must exist before any other endpoint, so they come first. Cost: three plan/review cycles instead of one.
- **P2 — One expand migration `0005_auth`** with `sessions`, `api_tokens`, `rate_limits`, `audit_log` and `users.totp_last_step`, marked `lossy-down`; 0001–0004 untouched (as M1.5 P27). No `passkeys` table. Cost: none.
- **P3 — Passkeys are deferred past M2.** The newest `webauthn-rs` on crates.io is `0.6.1-dev` (a pre-release), and the ceremony needs the SPA; password + TOTP covers 07 §2's M2 requirement ("passkeys stretch"). Cost: no phishing-resistant login in the first release.
- **P4 — The site key lives outside the database.** `auth.secret_key[_file]`; solo without one uses `<data>/secret.key` (created by `init` or the first start, `0600`); cluster mode requires it configured (config validation), because every node must use the same key and a database dump or `ferrite export` must not carry the key that opens the secrets in it (TOTP secrets now, plugin `secret` settings in M2a-2). Subkeys are HMAC-derived per purpose. Cost: cluster operators distribute one more secret; a lost or changed key leaves sessions and CSRF tokens working (they use per-session secrets) but makes stored TOTP secrets unreadable, so users re-enroll after `ferrite user disable-totp`.
- **P5 — Rate limits are DB-backed fixed windows, not `tower_governor`.** 07 §2 and 01 §8 require counters that hold across nodes; `governor`/`tower_governor` keep state per process. `RateLimitRepo::hit` is one upsert statement on the database clock. Cost: one write per login attempt; fixed windows allow up to 2× the limit across a window edge.
- **P6 — Token scopes are part of `Actor`.** `Actor { user, role, scopes }`; `require` checks the role, then the capability's scope; `require_read(area)` covers reads. Scopes are `<area>:<read|write>`, write implies read; a session has every scope. Keeps "capabilities checked in core" true for tokens too (07 §1). Cost: 26 `Actor { .. }` literals become `Actor::new`.
- **P7 — Sessions.** 32-byte random token in `ferrite_session` (`HttpOnly; SameSite=Lax; Path=/; Max-Age` 30 d), SHA-256 in the database, idle 7 d / absolute 30 d (07 §2), `last_seen_at` refreshed at most every 5 min (04 §5), no per-node cache (revocation is immediate everywhere). `Secure` is set only when `site.url` is `https://`, so local `http://localhost` development works; 07's unconditional `Secure` would drop the cookie there. Sessions are deleted on logout, password change (except the current one), role change, disable and delete. Cost: one session read per authenticated request.
- **P8 — CSRF and Origin.** Cookie-authenticated non-GET/HEAD requests need `X-CSRF-Token` = base64url(HMAC-SHA256(session `csrf_secret`, `"ferrite-csrf:v1:" + id_hash`)) **and** an `Origin` equal to the site origin (or, without `Origin`, a same-origin `Referer`); login and the TOTP login step check `Origin` too (login CSRF). Bearer requests are exempt. No CORS headers in M2a: the admin is same-origin and headless clients use tokens. Cost: browser apps on other origins cannot call the API directly.
- **P9 — TOTP.** RFC 6238 SHA-1, 6 digits, 30 s, skew 1 (what authenticator apps support; totp-rs defaults). Enrollment and the second login step are stateless sealed blobs (XChaCha20-Poly1305 under the site key, 10 / 5 min expiry), so no pending-state table; the secret is stored sealed in `users.totp_secret`; replays are refused by the conditional `advance_totp_step`. No recovery codes in M2a (operators run `ferrite user disable-totp`). Cost: a user without their device needs an operator.
- **P10 — Problem details.** `type` is the relative reference `/api/v1/problems/<slug>` (no product name or domain baked into responses). Mapping: `NotFound` → 404 `not-found`; `Forbidden(c)` → 403 `forbidden` (detail names `c`); `Invalid(m)` → 422 `validation` (`errors[0].detail = m`); `Conflict` → 412 `version-conflict` with `current`; `Unauthenticated` → 401 `unauthenticated` (login: `invalid-credentials`); `RateLimited` → 429 `rate-limited` + `Retry-After`; `Store(Busy)` → 503 `unavailable` + `Retry-After: 5`; `Store(UniqueViolation)` → 409 `conflict`; other store errors → 500 `internal` (logged, generic body). Malformed input is 400, missing `If-Match` 428, wrong media type 415, oversize 413. Cost: none.
- **P11 — `If-Match` only where a `version` exists.** Content (PATCH, DELETE, lifecycle POSTs, revision restore) requires `If-Match: "<version>"`; `ETag` carries it. Users, terms, menus (whole-tree PUT), redirects and settings have no version column and are last-write-wins, which 07's "resources carry `version`" does not cover. Cost: two admins editing the same menu at once lose one edit.
- **P12 — OpenAPI from DTOs, snapshot in the repo.** utoipa 6 + utoipa-axum 0.3 generate 3.1.0; DTOs live in `ferrite-http/src/api/`, so domain types stay free of API annotations (M1a R3). One explicit list struct per resource (stable schema names for the M2b TypeScript client). `crates/ferrite-http/openapi.json` is checked by a test; the CI drift check of the generated client is M2b. `Idempotency-Key` (07 §1, imports/uploads) arrives with uploads in M2a-2. Cost: DTO boilerplate.
- **P13 — Content API semantics.** `DELETE` trashes; `?force=true` deletes a trashed item permanently (WordPress's behaviour). `PATCH` omits fields to keep them; `slug: null` is rejected. Revision restore restores title, excerpt, body and fields, not meta (meta is plugin- and SEO-owned and has its own writers). `publish` accepts scheduled items. Cost: none.
- **P14 — Logins and e-mail.** Logins are `^[a-z0-9][a-z0-9._-]{0,59}$` after lowercasing and immutable after creation, so `/author/<login>/` URLs never move (no redirects needed); `user:<id>` is emitted on display-name and status changes and on delete. E-mail stays unique by the ASCII-lowercased `email_key` (M1a R12), deciding the M1a open item: non-ASCII case variants are distinct accounts, consistent with RFC 5321's case-sensitive local parts. Cost: `É@x` and `é@x` can be two accounts.
- **P15 — Passwords.** argon2id with argon2 0.6's defaults (m = 19 456 KiB, t = 2, p = 1), rehash on login when parameters differ (07 §2), 12..=1024 bytes, a dummy verify for unknown users, hashing on `spawn_blocking` under a per-process semaphore (`max(2, CPUs)`) so login floods cannot exhaust memory. `must_reset` users get a session limited to `me`, `logout` and `password`. Cost: ~20 MiB per concurrent hash.
- **P16 — User deletion and the last admin.** Deleting a user who authored content needs `reassign` (content and revisions move in the same `Tx`); nobody can demote, disable or delete the last active admin, or change their own role or status. The last-admin check is not serialized under READ COMMITTED (M1c-1 P2): two concurrent demotions can both pass. Cost: an operator then uses `ferrite user create`.
- **P17 — The CLI is a system path.** `UserService::operator()` performs create/reset/disable-TOTP without an actor (like `publish_due`); `ferrite user …` uses it. Generated passwords are printed once and force a reset; `--password-stdin` sets a password without printing. With SQLite these commands fail while `serve` holds the folder lock (as `seed`). Cost: no remote user bootstrap besides the CLI.
- **P18 — Content types and taxonomies are registered through core and announced by `types.changed`.** Type and taxonomy writes need `manage_settings`, validate names against the router (reserved words, route words, years, each other) and the current permalink structures, store the field schema as `{"fields": [...]}` (`{}` = none), and emit `types.changed` + `invalidate [all]`; the reloader rebuilds permalink rules and the route table on it. Older nodes treat the unknown kind as "invalidate keys" (M1.5 P28). Item `fields` are validated against the schema on every content write. Cost: a full cache flush per type change (rare).
- **P19 — Settings are an allowlist with validators in core.** `ferrite_core::settings::SETTINGS` lists the keys the API may read and write; `OptionService::set_many` validates and writes them in one `Tx`; `permalink.*` writes are validated against types and taxonomies inside the `Tx`, on every caller (closes the deferred item). Theme and plugin settings are M2a-2. Cost: new settings need a code change.
- **P20 — Previews at `/_preview/<id>`.** Handled by the public handler (the theme pipeline lives there), authenticated by the session cookie only, never cached, `noindex`; every failure is the shared 404 so drafts cannot be probed. `_preview` becomes a reserved top-level slug. Cost: a legacy item with slug `_preview` would be renamed on its next update (none exist).
- **P21 — Logged-in requests on the public site.** A valid session cookie makes the request logged in: `cache.logged_in = "bypass"` (default) renders without the cache and sends `Cache-Control: private, no-store`; `"per-user"` caches under `Variant::User(user id)`. Plugins see `is_logged_in = true`. An invalid cookie is ignored. Cost: one session lookup per public request that carries the cookie.
- **P22 — Audit log.** User, token, TOTP, type/taxonomy and settings writes append an audit row in the same `Tx` (no secrets in `details`). Login failures are not audited (rate limits and logs cover them). No retention job and no list endpoint in M2a-1 (the system API in M2a-2 lists it). Cost: the table grows slowly and unbounded until a retention rule is added.
- **P23 — `sessions.prune` is a built-in periodic job** (hourly, `ferrite-cluster`), deleting expired or idle sessions and rate-limit windows older than 1 h in batches (M1.5 R5); the shared session constants live in `ferrite-domain::auth` so `ferrite-cluster` needs no core dependency. Cost: none.
- **P24 — The API shares the process and layers with the public site.** `build_site` nests `/api/v1` before the public fallback; API responses never touch the page cache, always carry `Cache-Control: no-store` and the existing security headers; JSON bodies are capped at 4 MiB (TipTap documents of long posts). Cost: none.
- **P25 — No new crates in the workspace.** The API lives in `ferrite-http/src/api/`, auth and users in `ferrite-core`; crypto is RustCrypto + `getrandom` (pure Rust, matching the single static binary goal). Cost: `ferrite-core` gains `tokio` (for `spawn_blocking`) and crypto dependencies.
- **P26 — Not in M2a-1:** everything listed under "Next plan: M2a-2" and "M2b scope" below.
- **P27 — Multi-host sites stay on R25** (the cache key host is pinned to `site.url`), deferred to "Later" with multi-site: a second host needs per-host `site.url`, cookies and CSRF origins, which this milestone just pinned to one origin. Cost: one hostname per site.
- **P28 — The ROADMAP's "Admin approval flow for limits above host defaults"** and the other plugin-host follow-ups go to M2a-2 together with the install flow they belong to.
- **P29 — CSV without a dependency.** Redirect import/export uses a ~100-line RFC 4180 reader/writer in `api/csv.rs` (quoted fields, `""`, CRLF/LF); only three columns exist. Cost: none.
- **P30 — Cookies without `axum-extra`.** One cookie is read (`ferrite_session`) and two `Set-Cookie` shapes are written; a dependency is not worth it. Cost: none.

# M4-2 — Release: Self-Update, Rollback, ACME, Metrics, Release Builds Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** FerriteCMS can be released and operated:
- signed release builds for six targets and a multi-arch image on GHCR;
- a binary that updates and rolls itself back;
- built-in HTTPS for solo sites;
- Prometheus metrics and dashboard time series;
- a systemd unit, a cluster runbook, and a backward-compatibility CI job.

**Architecture:**
- **Updates and rollback:** `self-update` and `rollback` are operator CLI commands that replace the binary next to itself and keep `ferrite.prev`. `serve` writes `data/upgrade.json` whenever the binary version or schema changes at startup. Rollback reads that file.
- **Metrics:** a small dependency-free metrics registry in `ferrite-http` feeds an optional `/metrics` listener. A once-a-minute `node_metrics` row per node feeds a series API and the admin charts.
- **TLS:** ACME runs through `rustls-acme`, using TLS-ALPN-01 on the TLS listener.
- **Releases:** GitHub Actions builds, checksums and minisign-signs the release on a `v*` tag.

**Tech Stack:**
- Rust: tokio, axum, sqlx 0.9, rustls (`ring`), `minisign-verify`, `rustls-acme`, `jiff`.
- GitHub Actions; Docker buildx.
- systemd.
- Admin: React with Recharts (already used).

**P25: the release process.**
- Tags are `vX.Y.Z`, matching the workspace version. Releases are GitHub Releases on `softberries/ferritecms`.
- Each target gets one asset, `ferrite-<X.Y.Z>-<target>.tar.gz`, holding `ferrite`, `LICENSE*` (if present) and `README.md`.
- Each release also carries `SHA256SUMS` (sha256 of every asset) and `SHA256SUMS.minisig`, a minisign signature over that file.
- `--channel stable` means the newest non-draft, non-prerelease release. It is the only channel.
- **M4-2 creates no tag.** The first tag freezes migrations (m1a R10) and needs the license decision (BRIEF:268). Both are the user's call, and the exit lists them as the release gate.
- Reason: the digest found nothing specified.
- Cost if wrong: renaming assets later breaks `self-update` for older binaries.

**P26: signatures.**
- The minisign format. Verification uses the pure-Rust `minisign-verify` crate (exact version, checked with Context7).
- The public key is embedded at build time from `crates/ferrite/release.pub` with `include_str!`.
- The repository ships a placeholder that holds no key. With it, `self-update` refuses with exit 1 and "this build has no release key".
- Under the `test-seams` feature only, `FERRITE_TEST_RELEASE_PUBKEY` replaces the key.
- The private key lives only in the GitHub secrets `MINISIGN_SECRET_KEY` and `MINISIGN_PASSWORD`. The user creates them; the exit doc gives the commands.
- `self-update` checks the signature on `SHA256SUMS` first, then the asset's sha256.
- Reason: `D09:9-10`.
- Cost if wrong: rotating the key needs a release signed with the old key that carries the new one (documented).

**P27: build metadata, profile and targets.**
- `crates/ferrite/build.rs` emits `FERRITE_TARGET` (the target triple). `self-update` picks its asset from it.
- `[profile.release]` sets `lto = "thin"`, `codegen-units = 1` and `strip = "symbols"`.
- Release targets, per `D09:474-476`:
  - `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`;
  - `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`;
  - `aarch64-apple-darwin`, `x86_64-apple-darwin`.
- Each target is built on a native runner where one exists: `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-14` (arm), `macos-13` (x86). musl builds use the musl target on the matching Linux runner (with `musl-tools`; the implementer may use `cargo-zigbuild` if C dependencies need it).
- Every build runs `pnpm build` first, because the admin is embedded.
- Reason: cross-compiling wasmtime is avoidable with native runners.
- Cost if wrong: macOS runners cost CI minutes.

**P28: the crypto provider.**

Proof: `cargo tree -p ferrite -i aws-lc-sys -e normal` prints nothing.

**P29: time zones.**
- The `jiff` crate, with the IANA database bundled (`tzdb-bundle-always` or the equivalent feature), because distroless and musl images have no `/usr/share/zoneinfo`.
- `site.timezone` is validated as an IANA zone at config load, and an invalid zone is a config error.
- The `date(fmt)` filter formats in `site.timezone`. `date(fmt, tz="Europe/Warsaw")` overrides it.
- Permalink dates stay UTC (m1c2 R4).
- Reason: `RM:457`; jiff is already in the lockfile.
- Cost if wrong: binary size grows by the bundled tzdb (about 0.5 MB).

**P30: `upgrade.json` and snapshots.**
- `Store::migrate_up` returns `MigrateReport { applied: Vec<i64>, snapshot: Option<PathBuf> }`. The snapshot is SQLite's pre-migration file; Postgres returns `None`. Every caller is updated.
- `schema_meta` gets a key `last_binary_version`, written at every `serve` start after the startup check.
- When the stored value differs from `binary_version()`, or migrations were applied, `serve` (and `migrate up`) atomically writes `<data>/upgrade.json` (write a temp file, then rename) with:
  - `{"v":1, "from": "<prev binary or null>", "to": "<this binary>", "schema_from": N, "schema_to": M, "snapshot": "<relative path or null>", "at": "<RFC 3339>"}`.
- Pruning of pre-migration snapshots (keep 5) never deletes the snapshot that `upgrade.json` names.
- Reason: `D09:16-17`, which leaves the format and the writer open.
- Cost if wrong: one extra schema_meta key.

**P31: `ferrite self-update [--version X] [--check] [--yes] [--data DIR]`.**
- **Release lookup:** fetch metadata from the GitHub API (`https://api.github.com/repos/softberries/ferritecms/releases/latest` or `/tags/vX`). A hidden `--base-url` flag, test-seams only, points it at a local server.
- **Download and verify:** download `SHA256SUMS`, `.minisig` and this target's asset, then verify (P26).
- **Unpack and check:** unpack into a temp folder in the binary's own directory, then run the new binary's `--version`. With `--data`, also run its `migrate status --data DIR` and print the result.
- **Confirm:** ask for confirmation unless `--yes` is given; without a TTY, `--yes` is required.
- **Swap:** copy the running binary to `ferrite.prev` (replacing an older one), then atomically rename the new binary over the running one.
- **No restart:** it prints the restart command (`systemctl restart ferrite`, or "stop and start `ferrite serve`"). `serve` never updates itself, so no dedicated exit code is needed (this corrects `D09:14`).
- **Refusals:**
  - an older or equal `--version` (use `rollback`);
  - no asset for `FERRITE_TARGET`;
  - an unwritable binary directory, with a hint: run it as the binary's owner, outside the systemd sandbox.
- `--check` only prints whether a newer release exists.
- **Exit codes:** 0 updated or up to date; 2 an update is available (`--check`); 1 error.
- It works the same with Postgres. A cluster deploys images instead (runbook).
- Reason: `D09:3-27`, made concrete.
- Cost if wrong: there is no in-place update from the admin. That is a later item.

**P32: `ferrite rollback [--data DIR] [--schema] [--allow-lossy] [--restore-snapshot] [--yes]`.**
- **Binary rollback** (no `--schema`):
  - It requires `ferrite.prev` next to the running binary.
  - With `--data`, it runs `ferrite.prev migrate status --data DIR` first. Exit 3 (incompatible) refuses and says to use `--schema` with the newer binary.
  - It then swaps `ferrite` and `ferrite.prev` through a temp name, so running it twice re-upgrades, and prints the restart command.
- **`--schema`** (needs `--data`):
  - It must run as the binary named `to` in `upgrade.json`; otherwise exit 1.
  - With SQLite, `serve` must be stopped (folder lock).
  - Under the migrate lock it runs `migrate_down(schema_from, allow_lossy)`. A lossy step without `--allow-lossy` refuses and names `--restore-snapshot`.
  - It then swaps binaries as above.
- **`--restore-snapshot`** (with `--schema`, SQLite only; Postgres exits 1 and points to PITR):
  - It confirms first (`--yes`, or an interactive yes) and says content written since `at` is lost.
  - It moves `ferrite.db` and its `-wal`/`-shm` files to `backups/rolled-back-<ts>.db[-wal|-shm]`, never deleting them.
  - It copies the snapshot into place, then swaps binaries.
  - The install id stays the same, since this is the same install.
- **After any rollback** that used `upgrade.json`, the file is renamed to `upgrade-rolled-back-<ts>.json`.
- **Exit codes:** 0, 1, 3 (the previous binary cannot open this schema).
- Reason: `D09:29-63`. The "run with either binary" contradiction is settled as: binary rollback runs with either binary, `--schema` only with the newer one.
- Cost if wrong: a rollback chain longer than one step is not supported (as the design says).

**P33: ACME TLS (solo).**
- **Crate:** `rustls-acme` (exact version, on the ring provider, checked with Context7), TLS-ALPN-01 on the TLS listener, so no port 80 is needed for the challenge.
- **Config `[server.tls]`:**
  - `mode = "off" | "acme"` (default off);
  - `domains` (default: the host of `site.url`; `site.url` must be `https://`);
  - `contact` (a `mailto:` URI, required);
  - `directory = "production" | "staging" | "<url>"` (default production);
  - `listen` (default `0.0.0.0:443`);
  - `redirect_http` (optional address that answers only with 301 to https, for example `0.0.0.0:80`).
- **Startup:** cluster mode with `acme` is a config error. Certificates and the account key go in `<data>/tls/` (0600).
- **Listeners:** with TLS on, `server.listen` keeps serving plain HTTP. Bind it to loopback for the healthcheck; the docs recommend `127.0.0.1:8080`. That avoids teaching `healthcheck` TLS.
- **HSTS:** `Strict-Transport-Security: max-age=31536000` on TLS responses only (`D01:529`).
- **Tests:** an integration test against Pebble (`ghcr.io/letsencrypt/pebble`, pinned by digest) in Docker, gated by `FERRITE_TEST_PEBBLE=1` (skipped otherwise; the exit runs it), plus unit tests for config and the cluster refusal.
- Reason: `D09:429-432`.
- Cost if wrong: TLS-ALPN-01 needs the TLS port reachable from the internet, which is standard for 443.

**P34: the metrics registry and `/metrics`.**
- **Registry:** a hand-rolled one in `crates/ferrite-http/src/metrics.rs`, with no new dependency: atomic counters, gauges read by closures at scrape time, and fixed-bucket histograms. It renders Prometheus text format 0.0.4.
- **Families:**
  - `ferrite_build_info{version,target}` 1;
  - `ferrite_http_requests_total{class,status}`, where `class` is `page|api|admin|media|plugin|preview|other` and `status` is `2xx|3xx|4xx|5xx`;
  - `ferrite_http_request_duration_seconds{class}`, buckets .005 .01 .025 .05 .1 .25 .5 1 2.5 5 10;
  - `ferrite_page_cache_hits_total`, `ferrite_page_cache_misses_total`, `ferrite_page_cache_entries`, `ferrite_page_cache_bytes`;
  - `ferrite_plugin_hook_calls_total{plugin,hook}`, `ferrite_plugin_hook_failures_total{plugin,hook}`, `ferrite_plugin_hook_duration_seconds{plugin,hook}`, using the host's buckets .001 .005 .025 .1 .5;
  - `ferrite_jobs{status}`;
  - `ferrite_db_pool_connections{state="idle|used"}`;
  - `ferrite_nodes`;
  - `ferrite_page_views_total`.
- **No fuel family:** the plugin host has no fuel counter; that is noted as a follow-up.
- **Listener:** `/metrics` is served only on an optional separate listener `[server] metrics_listen = "127.0.0.1:9464"`, off by default. There is no auth, and it is never on the public site.
- **Page views:** successful (200) GET responses of public HTML pages that are not previews or logged-in requests and whose User-Agent does not match `bot|crawler|spider|slurp|preview` (case-insensitive). Nothing per visitor is kept.
- Reason: `D01:513-516`, `D09:467`.
- Cost if wrong: a hand-rolled registry lacks exemplars and summaries. Neither is needed.

**P35: `node_metrics` and the series API.**
- **Migration `0012_node_metrics`** on both backends, expand-only, with a `.down.sql`. Table `node_metrics`:
  - key: `node_id` id, `minute` timestamp, primary key (`node_id`, `minute`);
  - counts: `requests`, `errors_5xx`, `page_views`, `cache_hits`, `cache_misses`, `plugin_calls`, `plugin_failures`, `jobs_done`, `jobs_failed` (bigint);
  - latency: `p95_ms` (an int, upper bound of the bucket that holds the page p95).
- **Writing:** every node writes one row per minute, solo included, from deltas of the registry counters (a `serve` background task, not a job). On shutdown it flushes a partial minute.
- **Retention:** an hourly built-in prune keeps 7 days (`node_metrics.prune` in the prune family).
- **API:** `GET /api/v1/system/metrics/series?from&to&step=minute|hour|day[&node=<id>]` (capability `system:read`). It returns buckets summed over nodes (p95 is the max), with `step` limits: minute ≤ 24 h, hour ≤ 7 d, day ≤ 7 d. It uses utoipa DTOs and regenerates the OpenAPI snapshot.
- **Postgres contract tests**, plus SQLite.
- Reason: `D09:467-470`, with solo included because the dashboard needs it.
- Cost if wrong: about 10 000 rows per node per week.

**P36: dashboard charts.**
- The admin dashboard gets a "Traffic" card: page views and requests/errors as an area chart, 24 h / 7 d toggle. A "Performance" card: cache hit ratio and page p95.
- Both come from the series API. The existing "This node only" labels go where data is now cluster-wide.
- Charts follow 11 §8 and the design bar (memory: state-of-the-art, far better than WP), with empty and loading states, and are reduced-motion safe.
- Plugin hook latency over time stays a follow-up (RM:464; it needs per-plugin rows).

**P37: packaging.**

## Review Focus

1. **Update safety:**
   - a corrupt download, a bad signature, a wrong-target asset or an unwritable directory leaves the running binary untouched;
   - the rename is atomic;
   - `ferrite.prev` is always a runnable previous binary.

   Tests: Task 4 `self_update_refuses_bad_signature`, `self_update_keeps_binary_on_failure`.
2. **Rollback never loses data silently:**
   - `--restore-snapshot` asks first;
   - it moves, never deletes, the current database;
   - a lossy down without `--allow-lossy` refuses.

   Tests: Task 5.
3. **TLS correctness:**
   - HSTS only on TLS;
   - the redirect listener redirects only;
   - cluster mode with ACME is refused;
   - certificate files are 0600.

   Tests: Task 6.
4. **Metrics cost and privacy:**
   - the per-request counter path is lock-free;
   - page views store no IP and no user agent;
   - label sets stay bounded (plugin and hook names only, never URLs).

   Tests: Task 7.
5. **The series API across nodes:** sums are correct, the p95 max holds, step limits are enforced, and an empty range is handled (Task 8).

# M1.5 — Cluster Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** N identical `ferrite serve` nodes on one Postgres + shared media behave as one site: a save on node A is visible on node B within ~1 s (`LISTEN/NOTIFY` + outbox catch-up), background work runs through a leased job queue that survives a node dying mid-job, coarse operations take advisory locks, every node registers and heartbeats, themes and plugins ship as artifacts and hot-swap on every node, and plugin failures count cluster-wide. Solo (SQLite + local media) runs the same code paths at almost no cost.

**Architecture:** Coordination primitives that need a backend connection go into `ferrite-store` (new `JobRepo`, `NodeRepo`, `PluginFailureRepo`, `Store::subscribe`, `Store::try_lock`, one expand migration `0004_cluster` on both backends, contract-tested). A new crate `ferrite-cluster` (depends on `ferrite-store` + `ferrite-domain` only) holds the runtime parts: job runner, periodic scheduler, built-in prune handlers, node registry and startup validation. `ferrite-cache`'s `InvalidationLoop` gains notification wake-ups, reconnect catch-up with lost-history flush, and an `EventHook` through which the binary hot-swaps the theme, the plugin registry and the permalink rules/route table (all already behind `ArcSwap`). `ferrite-core` enqueues scheduled-publish jobs inside the scheduling transaction and gains `ExtensionService` (theme/plugin rows + events in one transaction under a lock). The binary composes everything in a refactored `serve::start`.

**Tech Stack:** sqlx 0.9 (`PgListener`, `PgAdvisoryLock`), tokio, tokio-util (`CancellationToken`), arc-swap 1, `tar` 0.4.46 (new; pure Rust, theme bundles), existing workspace crates. Docker Compose file format for the example (validated, not run locally).

**Spec:** `docs/design/04-cluster.md` (all sections), `docs/design/02-storage.md` §3–§9 (cluster tables, contract tests, expand/contract), `docs/design/05-plugin-host.md` §2, §8, §12, `docs/design/06-themes-rendering.md` §1, §6, `docs/design/09-operations.md` §3, §7, §8, `docs/design/01-architecture.md` §2. ## Global Constraints

M1c-1 P2: correctness under concurrency comes only from optimistic `version`, unique constraints + retry, and single-statement atomic store operations (the job claim is one statement). M1c-1 R3: an empty computed id set short-circuits. M1c-1 R5: `cluster.mode = "auto"` resolves to cluster only for Postgres + shareable media. M1b R2: the `artifacts` row is the source of truth for an artifact. M1c-2: the dependency-key contract in `ferrite-core/src/events.rs`; R10 (`permalink.*` writes emit `all`); R18/R19/R21 plugin deadline, volatility and grants; R24 gap skip + late set; R25 cache host pinned to `site.url`; R28/R32 render slots; P2 helper bridge. ## Review Focus

1. **A change committed while a node boots is never missed.** A theme activation, plugin enable or permalink change that commits between "node read the active theme/plugins/rules" and "invalidation cursor set" would leave that node on the old version forever; expected: the node converges within one poll. *Test in Task 10 (`boot_race_change_during_startup_is_applied`).*
2. **A poison job that kills its node every attempt goes dead instead of looping.** Each crash leaves an expired lease; reclaiming must not go past `max_attempts`. *Test in Task 1 (`jobs_expired_lease_at_max_attempts_goes_dead`).*
3. **A paused or partitioned node cannot overwrite the new owner's result.** Node A stalls past its lease, node B reclaims and completes; A's late `complete`/`fail`/`extend` must be a no-op, and A must stop its local handler when `extend` reports the lease lost. *Tests in Task 1 (`jobs_stale_lease_holder_cannot_write`) and Task 4 (`runner_cancels_handler_when_lease_lost`).*
4. **A bad theme or plugin version leaves every node on the previous working version.** Corrupt artifact bytes, a hash mismatch, a template syntax error or a component that fails to compile; expected: previous version keeps serving, failure visible in `nodes.meta`, no fallback to `blog` at runtime. *Tests in Task 10 (`bad_theme_activation_keeps_previous_theme`, `bad_plugin_update_keeps_previous_version`).*
5. **Two nodes started at once on an empty schema** (what `docker compose up` does): exactly one applies migrations, both come up and serve. *Test in Task 11 (`concurrent_first_start_migrates_once`).*

**Schema (both backends, physical types per 02 §5):** `jobs(id PK jobs_pkey, kind text NOT NULL, payload json NOT NULL, unique_key text NULL, run_at ts NOT NULL, priority int NOT NULL DEFAULT 0, status text NOT NULL CHECK IN ('queued','running','done','dead'), attempts int NOT NULL DEFAULT 0, max_attempts int NOT NULL DEFAULT 5 CHECK (max_attempts >= 1), locked_by text NULL, locked_until ts NULL, last_error text NULL, created_at ts NOT NULL, finished_at ts NULL)`, `UNIQUE INDEX jobs_unique_key_uq (unique_key)` (NULLs distinct on both), `INDEX jobs_claim_idx (status, run_at)` (Postgres partial `WHERE status IN ('queued','running')`), `INDEX jobs_finished_idx (finished_at)`. Same migration creates `nodes(id PK nodes_pkey, name text NOT NULL, version text NOT NULL, schema_version bigint NOT NULL, started_at ts NOT NULL, heartbeat_at ts NOT NULL, meta json NOT NULL DEFAULT '{}')` + `INDEX nodes_heartbeat_idx (heartbeat_at)` (repo in Task 3). Text keys `COLLATE "C"` on Postgres. Down drops both tables and carries `-- ferrite:lossy-down` (queued work is lost).

**Semantics:**
- Validation before SQL (`Invalid`, no poisoning): `kind` matches `[a-z0-9._-]{1,64}`; `unique_key` ≤ 200 chars; payload passes `validate_json` and is an object; `kinds` 1..=`MAX_CLAIM_KINDS`; `limit` 1..=`MAX_CLAIM`; `max_attempts` 1..=100; `error` has NUL replaced by U+FFFD and is cut to `MAX_JOB_ERROR` bytes on a char boundary (handler text is not caller-validated input, so it is sanitised, not refused).
- **Claim, Postgres** — one call runs two statements: first the reaper `UPDATE jobs SET status='dead', last_error='lease expired after attempt <attempts> on node <locked_by>', finished_at=now(), locked_by=NULL, locked_until=NULL WHERE status='running' AND locked_until < now() AND attempts >= max_attempts AND kind = ANY($kinds)` (P7), then the claim as a `MATERIALIZED` CTE (P5):
  ```sql
  WITH next AS MATERIALIZED (
    SELECT id FROM jobs
    WHERE kind = ANY($kinds)
      AND ((status = 'queued' AND run_at <= now())
        OR (status = 'running' AND locked_until < now() AND attempts < max_attempts))
    ORDER BY priority DESC, run_at, id
    LIMIT $limit
    FOR UPDATE SKIP LOCKED)
  UPDATE jobs SET status='running', locked_by=$node, locked_until=now()+$lease, attempts=attempts+1
  FROM next WHERE jobs.id = next.id
  RETURNING jobs.<explicit column list>;
  ```
  Result sorted by `(priority DESC, run_at, id)` in Rust (`RETURNING` order is unspecified).
- **Claim, SQLite** — same predicates without `FOR UPDATE SKIP LOCKED` (`kind IN (SELECT value FROM json_each(?))`), reaper + `UPDATE … WHERE id IN (SELECT … LIMIT ?) RETURNING …` in one `atomic!` on the writer. Before touching the writer, one `SELECT EXISTS(…due…)` on the reader pool; no due job → return empty without taking the writer (C7: an idle solo node does not take the write lock every second).
- All lease-holder writes are conditional on `id = $id AND status = 'running' AND locked_by = $node AND attempts = $attempt` (P6). `complete` → `done`, `finished_at = now`, lock columns NULL. `fail` → `dead` (with `finished_at`) when `permanent` or `attempts >= max_attempts`, else `queued` with `run_at = now + job_backoff(attempts)`, `last_error` set, lock columns NULL; Postgres computes the backoff in SQL as `now() + make_interval(secs => LEAST(power(2, attempts) * 10, 3600))`, SQLite in Rust with `job_backoff`. `release` → `queued`, `run_at = now + delay`, lock columns NULL, `attempts = attempts - 1` when `count_attempt == false`. `extend` sets `locked_until = now + lease`.
- `job_backoff(a) = min(2^a × 10 s, 3600 s)` for `a >= 1`; `a <= 0` → 10 s.
- Decoding reads columns by name (unknown extra columns ignored — rolling deploys, 04 §9).

**Tests** (`crates/ferrite-store-tests/src/job.rs`, both backends unless marked):

- `jobs_expired_lease_is_reclaimed` — claim with lease 1 s, sleep 1.2 s, claim by node B returns it with `attempts = 2`, `locked_by = B`.
- `jobs_expired_lease_at_max_attempts_goes_dead` (Review Focus 2) — `max_attempts = 2`; claim, expire, reclaim (attempts 2), expire; next claim returns nothing and the job is `Dead` with `last_error` containing `lease expired after attempt 2`.

**Runner behaviour:** one claim loop per node; claims `min(free slots, MAX_CLAIM)` with `kinds` = the registered handler kinds (P5); waits for `idle_poll`, a job notice (when `listen`, via `subscribe(Jobs)`, resubscribing with 1 s→30 s backoff), or a freed slot. Per job: read `payload.v` (absent → 1; not an integer → `fail(permanent)` with "payload has no valid v"); unsupported `v` → `release(delay = job_backoff(attempts), count_attempt = false)` (P5); otherwise run under `tokio::time::timeout(handler.timeout())`. Every `extend_every` the runner extends all in-flight leases; `extend` → `false` cancels that job's future (drop) without writing (Review Focus 3). Outcomes: `Ok` → `complete`; `Retry(e)` or timeout → `fail(e, false)`; `Permanent(e)` → `fail(e, true)`; a panicking handler (`JoinError::is_panic` of the spawned job task) → `fail("handler panicked", false)`. Shutdown (P10): on `stop` no new claims; in-flight jobs get `drain` (9 s); then remaining futures are dropped and each lease is `release(0, count_attempt = false)`. Store errors are logged and retried on the next tick; the runner never panics. Tracing span `job{kind, id, attempt}`.

## Plan rulings

- **P1 — Implementations follow the backend, not the mode.** Job claim, locks and notifications are chosen by `Store` backend (Postgres: `SKIP LOCKED`, advisory locks, `LISTEN/NOTIFY`; SQLite: single-writer claim, in-process mutex, no subscription), because a solo node on Postgres still shares a database that other processes (`ferrite migrate`, a second node) can reach. `cluster.mode` only decides: listening for notifications, the solo single-live-node rule (P15), and whether `data/themes/` folders are read (P17). Cost: solo-on-Postgres sends NOTIFYs nobody listens to (one cheap call per event).
- **P2 — NOTIFY from the writing statement.** `pg_notify` runs inside the `INSERT … RETURNING` of `events.append` / `jobs.enqueue`; Postgres delivers it only at commit, which is exactly 04's "after commit" and cannot be forgotten by a write path. Channels are database-wide while sites are separated by schema, so channels are `ferrite_events` / `ferrite_jobs` without a schema and `ferrite_events_<schema>` / `ferrite_jobs_<schema>` with one, lowercased (works whether or not sqlx quotes the `LISTEN` identifier). Payload: the seq (events), the kind (jobs); receivers treat both as hints only. `database.schema` is capped at 48 bytes so the channel fits Postgres' 63-byte identifier limit. Cost: two schemas differing only in case share a channel (extra polls, no wrong results).
- **P3 — Wake-ups are hints; history is checked on reconnect.** A notice triggers one immediate poll (coalesced). A `Reconnected` notice or the first successful poll after failed polls runs a history check via the new `EventRepo::min_seq`; `min_seq > last_seq + 1` flushes the cache, reloads node state (`on_history_lost`) and moves the cursor to `min_seq - 1`. The late-probe algorithm is unchanged; its bound is documented and tested. Cost: one `min_seq` query per reconnect.
- **P4 — `idle_in_transaction_session_timeout = 60s`** on Postgres app connections (well under the 10-minute `LATE_HORIZON`; core never holds a `Tx` across slow work, M1c-1 P1). A `Tx` busy with statements longer than 10 minutes is not bounded (`transaction_timeout` needs PG 17; the floor is 15). Cost: a `Tx` idle for 60 s is killed and its caller gets an error.
- **P5 — Claim only known kinds; unknown payload versions go back without an attempt.** `claim` filters `kind = ANY($kinds)` so an old node never touches a new kind (04 §9's "re-queue with backoff" would burn attempts and send N+1 jobs to `dead`); an unknown `payload.v` is released after `job_backoff(attempts)` with the attempt refunded; a payload without `v` is version 1. The claim is a `MATERIALIZED` CTE instead of 04's `IN (subquery)` so the `LIMIT … FOR UPDATE SKIP LOCKED` subquery is evaluated once, by construction. Cost: a kind no running node knows waits forever (visible as queued).
- **P6 — Lease token = (job id, node id, attempts).** Every lease-holder write (`extend`, `complete`, `fail`, `release`) is conditional on it, so a node whose lease lapsed, even one that reclaimed its own job, cannot overwrite the current attempt. Cost: none.
- **P7 — An expired lease at `max_attempts` goes `dead`** (reaper statement in `claim`) instead of being reclaimed past the limit. 04's claim SQL never stops reclaiming a job that kills its node. Cost: one extra UPDATE per claim call (index range scan, usually zero rows).
- **P8 — No `failed` status.** 02 lists `failed`, but 04's semantics never produce it (retry = `queued` + `last_error`; terminal = `dead`); the CHECK allows `queued`, `running`, `done`, `dead`. Cost: adding a status later needs a SQLite table rebuild.
- **P9 — The runner renews every lease; handlers have a timeout.** All in-flight leases are extended every 20 s (handlers need no lease code); each handler has `timeout()` (default 300 s) so a hung handler on a live node fails and retries instead of holding its lease forever. `JobError::Permanent` goes straight to `dead`. Cost: an import (M3) must override `timeout()`.
- **P10 — Shutdown releases unfinished jobs.** First signal stops claiming; in-flight jobs get 9 s (concurrent with the HTTP drain); the rest are released with the attempt refunded, so another node takes them at once instead of after the 60 s lease. Cost: a job that cannot finish in 9 s restarts elsewhere (handlers are idempotent, 04 §6).
- **P11 — Periodic scheduling uses the database clock.** Each node ticks every 10 s, reads `db_now`, and inserts `<kind>:<floor(db_now / period) × period, unix seconds>` with `run_at` = period start; `ON CONFLICT DO NOTHING` means one row per period cluster-wide. M1.5 periodics: `events.prune`, `jobs.prune`, `nodes.prune`, `plugin_failures.prune` (hourly), `content.publish_due` (30 s). Cost: periodic job rows accumulate until `jobs.prune` (7 days).
- **P12 — Scheduled publishing.** `schedule` enqueues `content.publish_scheduled` in its own `Tx` with `unique_key = "publish:<id>:<scheduled_at unix micros>"` (04's `publish:<id>` would block rescheduling an item whose earlier job row still exists) and `run_at = scheduled_at`; the handler publishes only if the item is still scheduled for that time. The per-node 30 s ticker becomes the periodic `content.publish_due` job (safety net for items scheduled before M1.5 or by an older binary). Cost: one extra row per (re)schedule.
- **P13 — Advisory locks.** Session-level `PgAdvisoryLock::new("ferrite:<schema>:<name>")` (sqlx HKDF key, scoped by schema because advisory locks are database-wide), on a dedicated connection per held lock (released for certain when the connection closes, including on a crash; a pooled connection could carry the lock back into the pool). Waiting polls `try_lock` every 250 ms; names `migrate` (5 min wait), `extensions` (30 s), `import` (reserved, M3). SQLite: in-process mutex per store. Cost: one connection per held lock.
- **P14 — Node registry values.** Heartbeat 10 s, stale after 30 s (3×, 02 §4), rows pruned 24 h after the last heartbeat, deregistered on clean shutdown. Name: `cluster.node_name`, else `$HOSTNAME-<pid>`, else `node-<pid>`. Clock skew is measured against `SELECT now()` at the round trip's midpoint and only warned about above 2 s (at join and when it crosses the threshold). `nodes.meta`: `site_id`, `site_url`, `mode`, `clock_skew_ms`, `theme`, `plugins`, `permalinks_error`.
- **P15 — Startup refusals.** A live node with a different `site_id` (schema_meta replaced under running nodes, e.g. a restore) or a different `site.url` (the realistic sign of a wrong `database.schema`/`search_path`; 04's literal check cannot fire for that case because both nodes read the same `schema_meta`) refuses start. In solo mode another live node is waited for up to 35 s (a crashed predecessor goes stale in 30 s), then refused. Cost: changing `site.url` needs all old nodes stopped (or 30 s after the last one stops).
- **P16 — `cluster.workers`:** default `max(2, available_parallelism)` (04's "default = CPU count, min 2"), explicit values 1..=256.
- **P17 — Theme bundles are plain deterministic tar** (`tar` 0.4.46, ustar, sorted, zeroed metadata), artifact kind `theme`, mime `application/x-tar`, unpacked in memory with the folder limits. Not `tar.zst` (06 §1): zstd needs a C library and themes are ≤ 20 MiB; the mime type leaves room for a compressed format later. In cluster mode `data/themes/` is ignored (C5); solo keeps it as a fallback for theme development. Cost: larger artifacts.
- **P18 — Hot swap off the event loop, double flush, keep the old version on failure.** Reloads run on one background task (coalesced, re-read from the database); the loop flushes on the event and the reloader flushes again after each swap. A theme, plugin version or permalink set that fails to load keeps the current one on that node and is reported in `nodes.meta` (04 §8); the startup-only fallback to `blog` is not used at runtime. The previous theme's assets stay served until the next swap. Cost: two flushes per change.
- **P19 — No on-disk artifact or precompiled-component cache in M1.5.** Reuse is in memory by artifact hash; a restart re-fetches and recompiles. 04 §8's precompiled cache needs `unsafe` `Component::deserialize`, and the plain byte cache saves little next to the compile. Cost: slower restarts with many plugins (M4 revisit).
- **P20 — Shared failure counters.** The host reports each failure to a `FailureSink`; the node buffers and every 5 s upserts 1-minute buckets (bucket time from the database clock), then checks the sum over `plugins.failure_window` against `plugins.disable_after_failures`; `auto_disable` is a conditional UPDATE, so exactly one node emits `plugin.disabled` (keys `[name, reason]`). The per-node in-memory disable stays. Enabling a plugin clears its counters in the same `Tx`. Counter retention `max(24 h, 2 × window)`. Cost: cluster-wide disable lags up to ~5 s behind the threshold.
- **P21 — Install/activation writes live in core, without a CLI.** `ExtensionService` writes artifact row + theme/plugin row + event in one `Tx` under the `extensions` lock; the binary's `install_theme_dir` / `install_plugin_file` upload the bytes first. The `ferrite theme|plugin` commands stay M2 (09 §8); tests and the exit check call the library functions. Cost: operators cannot install from the CLI until M2.
- **P22 — The invalidation cursor is set before node state is read.** `serve` creates the `InvalidationLoop` (cursor) before reading permalink options, the theme and the plugins, so a change committed during boot is applied by the first poll instead of being missed forever (the M1c-2 order read them first). Cost: a boot-time change may be applied twice (idempotent).
- **P23 — R14 (template memory) stays deferred, now to M4 (render worker).** A per-thread counting allocator cannot fail one allocation gracefully (a `GlobalAlloc` returning null aborts the process through `handle_alloc_error`), and MiniJinja has no check point other than fuel where a budget could stop the render; the real fix is rendering in a separate worker process with an OS memory limit, which is outside this milestone. M1.5 adds no untrusted install path: themes are still installed only by an operator calling `install_theme_dir` (the upload UI is M2). New risk recorded: with hot swap, a hostile theme reaches every node at once instead of one restarted node. Cost: an operator-installed hostile theme can still OOM the nodes.
- **P24 — Compose example verification.** Locally: the `cluster_example_config_is_valid` test (config + env through `ferrite_config::load`, plus `ferrite config check`); in CI: `docker compose … config --quiet` and `docker build`. `docker compose up` is not run in M1.5. Cost: runtime problems in the compose wiring (Caddy health checks, MinIO bucket init) surface only when someone runs it.
- **P25 — "Killing a node mid-job" is verified in process.** The crash is `RunningNode::abort()` (every task dropped, nothing released or deregistered) plus `pg_terminate_backend` on that node's connections, which leaves the database exactly as a killed process does. No production job runs long enough to SIGKILL a child process reliably mid-job. Cost: OS-level kill behaviour (socket teardown timing) is not exercised.
- **P26 — Not in M1.5:** `node.drain` handling (stays a no-op), `plugin.action` jobs (no action hooks are dispatched yet; M2), `artifacts.gc` (M4), `sessions.prune` (sessions are M2), `revisions.prune` (core prunes on save), `/metrics` and `node_metrics` (M4), PgBouncer transaction pooling (listeners and locks need direct connections; still unsupported, 02 §6).
- **P27 — New migration `0004_cluster`, not edits to `0001`.** R10 would allow editing `0001`, but a new expand migration exercises the upgrade path the cluster depends on (an existing database gains the tables) and the lint. Its down is `lossy-down` (queued jobs). Cost: none.
- **P28 — Events are versioned by kind, not by payload.** `events` rows have no payload column (kind + keys, 02 §4), so 04 §9's `{"v":1,…}` applies to job payloads only; a new event shape gets a new kind, and the loop's existing rule (unknown kind → invalidate its keys) is the compatibility rule. Cost: none.

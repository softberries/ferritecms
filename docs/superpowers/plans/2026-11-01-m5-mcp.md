# M5 — AI assistants (MCP) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every FerriteCMS site serves an authenticated MCP endpoint at `/mcp` (OAuth 2.1 + personal API tokens) with tools that manage the whole site, plus the admin screens and the docs/website story around it.

**Architecture:** `rmcp` Streamable HTTP server in stateless mode inside `ferrite-http`; tools are thin adapters over the existing `ferrite-core` services, run as the caller's `Actor`. A built-in OAuth authorization server (`ferrite-core::oauth` + `ferrite-http::oauth`) issues grant-bound `api_tokens` rows; the admin SPA provides consent, connected apps and settings.

**Tech Stack:** Rust 2024, axum 0.8, `rmcp` 3.8 (`server`, `macros`, `schemars`, `transport-streamable-http-server`), `schemars` 1, sqlx (SQLite + Postgres), React/TanStack admin, Vitest, Playwright.

**Spec:** `docs/design/12-mcp.md` (read it first; it wins over this plan on behaviour).

## Global Constraints

- Migration `0013_oauth` on **both** backends, `-- ferrite:phase expand`, with `.down.sql`; contract tests on both (`FERRITE_TEST_PG_URL=postgres://ferrite@localhost:54329/ferrite_test`).
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings`; `thiserror` in libraries, `anyhow` only in `crates/ferrite`; no `allow(dead_code)`; `unwrap_used`/`expect_used` stay warnings-free in non-test code.
- Capabilities are checked in core, never in handlers or tools.
- REST API changes: DTOs with `utoipa` annotations; regenerate `crates/ferrite-http/openapi.json` with `FERRITE_UPDATE_OPENAPI=1 cargo test -p ferrite-http --test api openapi`; then `pnpm -C admin gen:api` (or the repo's schema generation script) for `admin/src/api/schema.d.ts`.
- Token values: OAuth access tokens 1 h, codes 60 s, pending requests 10 min, grants 30 days sliding; client ids `ferc_` + 22 base64url; DCR 10/IP/hour; token endpoint 30/IP/min; tools 120/user/min.
- Admin: i18n keys in `admin/src/i18n/en/*.json`; design rules of `docs/design/11-admin-ui.md` (no raw colours outside tokens, 44 px touch targets, axe clean).
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- A client that sends `resource` with a trailing slash, or none at all → accepted (spec allows); a different resource → `invalid_target`.
- A loopback redirect URI with a different port than registered → accepted (RFC 8252); a different path or host → refused with an error page, never a redirect.
- A refresh token used twice (after rotation) → the grant is revoked and its access tokens stop working immediately.
- An OAuth access token sent to `/api/v1/...` → 401 `invalid_token`; a personal token still works on both.
- A contributor connecting an assistant → can create drafts and submit for review, cannot publish; the tool error names the missing capability.

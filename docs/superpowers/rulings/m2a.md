# M2a-1 REST API core & auth — plan and controller rulings

Decisions made while planning and executing docs/superpowers/plans/2026-10-23-m2a-api.md (subagent-driven). Format: ruling — reason — cost if wrong. P = plan rulings, F = pre-flight findings (all accepted as proposed by R4; one line each), R = controller rulings during execution. Where the code differs from a plan ruling's text, the line says "as built".

## Plan rulings

- Plan ruling P1: M2 is split three ways: M2a-1 (this plan: auth, API core, users, content/types/terms/menus/redirects/settings endpoints, previews, logged-in requests; 14 tasks), M2a-2 (extensions, plugin API extras, media, comments, system endpoints, hardening, remaining deferred items; own plan), M2b (admin SPA) — one backend plan would be ~28 tasks, and auth plus the API conventions must exist before any other endpoint — cost: three plan/review cycles instead of one.
- Plan ruling P2: one expand migration `0005_auth` (`sessions`, `api_tokens`, `rate_limits`, `audit_log`, `users.totp_last_step`), marked `lossy-down`; 0001–0004 untouched; no `passkeys` table — exercises the upgrade path as M1.5 P27 did — cost: none.
- Plan ruling P3: passkeys deferred past M2 — the newest `webauthn-rs` is `0.6.1-dev` (a pre-release) and the ceremony needs the SPA; password + TOTP covers 07 §2's M2 requirement — cost: no phishing-resistant login in the first release.
- Plan ruling P4: the site key lives outside the database (`auth.secret_key[_file]`; solo falls back to `<data>/secret.key`, created by `init` or the first start, `0600`; cluster mode requires it), with HMAC-derived subkeys per purpose — every node needs the same key, and a dump or export must not carry the key that opens the secrets in it — cost: one more secret for cluster operators; a lost key makes stored TOTP secrets unreadable (users re-enroll after `ferrite user disable-totp`), sessions and CSRF keep working.
- Plan ruling P5: rate limits are DB-backed fixed windows (`RateLimitRepo::hit`, one upsert on the database clock), not `tower_governor` — 07 §2 and 01 §8 require counters that hold across nodes, and `governor` keeps state per process — cost: one write per login attempt; up to 2× the limit across a window edge.
- Plan ruling P6: token scopes are part of `Actor { user, role, scopes }`; `require` checks the role, then the capability's scope; `require_read(area)` covers reads; scopes are `<area>:<read|write>`, write implies read; a session holds every scope — keeps "capabilities checked in core" true for tokens — cost: the `Actor { .. }` literals became `Actor::new` (16 sites, F1).
- Plan ruling P7: sessions: 32 random bytes in `ferrite_session` (`HttpOnly; SameSite=Lax; Path=/; Max-Age` 30 d), SHA-256 in the database, idle 7 d / absolute 30 d, `last_seen_at` at most every 5 min, no per-node cache; `Secure` only for an `https` `site.url`; deleted on logout, password change (except the current one), role change, disable and delete — revocation must be immediate everywhere, and an unconditional `Secure` drops the cookie on `http://localhost` — cost: one session read per authenticated request.
- Plan ruling P8: cookie-authenticated non-GET/HEAD requests need `X-CSRF-Token` = base64url(HMAC-SHA256(session `csrf_secret`, `"ferrite-csrf:v1:" + id_hash`)) and an `Origin` equal to the site origin (else a same-origin `Referer`); login and the TOTP login step check `Origin` (login CSRF); bearer requests are exempt; no CORS — the admin is same-origin and headless clients use tokens — cost: browser apps on other origins cannot call the API.
- Plan ruling P9: TOTP is RFC 6238 SHA-1, 6 digits, 30 s, skew 1; enrollment and the login challenge are stateless sealed blobs (XChaCha20-Poly1305 under the site key, 10 / 5 min); the secret is stored sealed; replays are refused by the conditional `advance_totp_step`; no recovery codes (operators run `ferrite user disable-totp`) — what authenticator apps support, and no pending-state table — cost: a user without their device needs an operator.
- Plan ruling P10: problem details with `type` = `/api/v1/problems/<slug>`; NotFound 404, Forbidden 403 (detail names the capability or scope), Invalid 422 `validation`, Conflict 412 with `current`, Unauthenticated 401 (login: `invalid-credentials`), RateLimited 429 + `Retry-After`, Busy 503 + `Retry-After: 5`, UniqueViolation 409 `conflict`, other store errors 500 `internal`; malformed input 400, missing `If-Match` 428, wrong media type 415, oversize 413 — no product name or domain in responses — cost: none. As built the 412 slug is `precondition-failed` (plan text: `version-conflict`) and the 503 slug is `busy` (plan text: `unavailable`); 07 §1, `problem.rs` and the OpenAPI snapshot use the built names.
- Plan ruling P11: `If-Match` only where a `version` exists: content (PATCH, DELETE, lifecycle POSTs, revision restore); users, terms, menus (whole-tree PUT), redirects and settings are last-write-wins — those tables have no version column — cost: two admins editing one menu at once lose one edit.
- Plan ruling P12: OpenAPI 3.1.0 from DTOs with utoipa 6 + utoipa-axum 0.3; DTOs in `ferrite-http/src/api/` (domain types stay free of API annotations, M1a R3), one list struct per resource; `crates/ferrite-http/openapi.json` checked by a test; the TypeScript client drift check is M2b; `Idempotency-Key` arrives with uploads in M2a-2 — stable schema names for the M2b client — cost: DTO boilerplate.
- Plan ruling P13: content API semantics: `DELETE` trashes, `?force=true` deletes a trashed item; `PATCH` keeps omitted fields, `slug: null` is rejected; revision restore restores title, excerpt, body and fields, not meta; `publish` accepts scheduled items — WordPress's behaviour; meta has its own writers — cost: none.
- Plan ruling P14: logins are `^[a-z0-9][a-z0-9._-]{0,59}$` after lowercasing and immutable; `user:<id>` on display-name and status changes and on delete; e-mail unique by the ASCII-lowercased `email_key`, so non-ASCII case variants are distinct accounts (closes the M1a open item) — `/author/<login>/` never moves; consistent with RFC 5321 — cost: `É@x` and `é@x` can be two accounts.
- Plan ruling P15: passwords: argon2id with argon2 0.6's defaults (m = 19 456 KiB, t = 2, p = 1), rehash on login, 12..=1024 bytes, a dummy verify for unknown users, hashing on `spawn_blocking` under a `max(2, CPUs)` semaphore; `must_reset` sessions limited to `me`, `logout` and `password` — login floods must not exhaust memory or reveal accounts — cost: ~20 MiB per concurrent hash.
- Plan ruling P16: deleting a user who authored content needs `reassign` (content and revisions move in the same `Tx`); nobody can demote, disable or delete the last active admin, or change their own role or status; the last-admin check is not serialized under READ COMMITTED — M1c-1 P2 — cost: two concurrent demotions can both pass; an operator then uses `ferrite user create`.
- Plan ruling P17: the CLI is a system path: `UserService::operator()` creates, resets passwords and disables TOTP without an actor; generated passwords are printed once and force a reset; `--password-stdin` sets one without printing; with SQLite the commands fail while `serve` holds the folder lock — the first admin and a locked-out admin need a way in — cost: no remote user bootstrap besides the CLI.
- Plan ruling P18: content types and taxonomies are registered through core (`manage_settings`), names checked against router words, years, each other and the permalink structures, the field schema stored as `{"fields": [...]}` (`{}` = none), writes emit `types.changed` + `invalidate [all]`, and the reloader rebuilds permalink rules and routes; older nodes treat the unknown kind as "invalidate keys"; item `fields` are validated on every content write — one rule set for every caller — cost: a full cache flush per type change (rare).
- Plan ruling P19: settings are an allowlist with validators in core (`ferrite_core::settings::SETTINGS`); `OptionService::set_many` validates and writes them in one `Tx`; `permalink.*` writes are validated against types and taxonomies inside the `Tx` on every caller (closes the deferred item); theme and plugin settings are M2a-2 — no unvalidated option write from the API — cost: new settings need a code change.
- Plan ruling P20: previews at `/_preview/<id>`, handled by the public handler, authenticated by the session cookie only, never cached, `noindex`, every failure the shared 404; `_preview` becomes a reserved top-level slug — the theme pipeline lives there and drafts must not be probeable — cost: a legacy item with slug `_preview` would be renamed on its next update (none exist).
- Plan ruling P21: a valid session cookie makes a public request logged in: `cache.logged_in = "bypass"` (default) renders without the cache and sends `Cache-Control: private, no-store`; `"per-user"` caches under `Variant::User(user id)`; plugins see `is_logged_in = true`; an invalid cookie is ignored — logged-in views must never fill anonymous entries — cost: one session lookup per public request that carries the cookie.
- Plan ruling P22: user, token, TOTP, type/taxonomy and settings writes append an audit row in the same `Tx` (no secrets); login failures are not audited; no retention job and no list endpoint in M2a-1 (`GET /system/audit` is M2a-2) — rate limits and logs cover failures — cost: the table grows slowly until a retention rule exists.
- Plan ruling P23: `sessions.prune` is a built-in hourly job in `ferrite-cluster` (expired or idle sessions, rate-limit windows older than 1 h, in batches, M1.5 R5); session constants live in `ferrite-domain::auth` — `ferrite-cluster` needs no core dependency — cost: none.
- Plan ruling P24: the API shares the process and layers with the public site: `build_site` merges `/api/v1` before the public fallback; API responses never touch the page cache, always carry `Cache-Control: no-store` and the security headers; JSON bodies ≤ 4 MiB — TipTap documents of long posts — cost: none.
- Plan ruling P25: no new crates: the API lives in `ferrite-http/src/api/`, auth and users in `ferrite-core`; crypto is RustCrypto + `getrandom` — pure Rust for the single static binary — cost: `ferrite-core` gains `tokio` and crypto dependencies.
- Plan ruling P26: not in M2a-1: everything in the M2a-2 outline and the M2b scope (plan, end) — scope — cost: listed in the roadmap.
- Plan ruling P27: multi-host sites stay on M1c-2 R25 (cache-key host pinned to `site.url`), deferred to "Later" with multi-site — a second host needs per-host `site.url`, cookies and CSRF origins, which this milestone pinned to one origin — cost: one hostname per site.
- Plan ruling P28: the ROADMAP's "admin approval flow for limits above host defaults" and the other plugin-host follow-ups go to M2a-2 with the install flow they belong to — scope — cost: none.
- Plan ruling P29: redirect CSV import/export uses a hand-written RFC 4180 reader/writer (`api/csv.rs`: quoted fields, `""`, CRLF/LF; three columns) — no dependency for three columns — cost: none.
- Plan ruling P30: cookies are read and written by hand, no `axum-extra` — one cookie read and two `Set-Cookie` shapes — cost: none.

## Pre-flight findings (accepted by R4)

- F1: 16 `Actor {` literal sites (not 26); `events::USER_KEY` read as `events::user_key` — counts are cosmetic.
- F2: each task adds the workspace pin and crate dependency it first uses, so every task compiles on its own.
- F3: incomplete Files lists (T2, T3, T8–T12) are in scope for those tasks, not scope creep.
- F4: `UserRepo::set_totp(id, Option<&Secret>)` sets/clears the secret and resets `totp_last_step` in one statement; `update` writes neither TOTP column.
- F5: `UserRepo::get_for_update`; every user read-modify-write (login bookkeeping included) reads the row with it inside its `Tx`, because `update` is unversioned.
- F6: `RateHit` carries the database `now`; `Retry-After = ceil(reset_at − now)` clamped to 1..=window.
- F7: login buckets are `login:user:<32 hex of a keyed HMAC of the trimmed, ASCII-lowercased input>`; inputs over 254 bytes are `Unauthenticated` without a hit; login and e-mail are distinct buckets.
- F8: IP rate-limit buckets mask IPv6 to /64; `Session.ip_hash` keeps the full address.
- F9: rate-limit tests spread attempts over several logins, and the API harness injects `ClientIp`.
- F10: rate-limit window tests align to a window boundary first (1 h window for concurrency, 2 s for reset).
- F11: the TOTP issuer is the site title without `:`, trimmed, falling back to `FerriteCMS`, fixed at boot; `totp_setup` while TOTP is on is `Invalid("disable TOTP first")`.
- F12: `AuthService::issue_session` exists; a password change issues a new session after the check; `keep_session` is a session `id_hash`.
- F13: T7's must-reset test uses `POST /auth/totp/setup`; T8 adds the content assertion.
- F14: handlers use relative `#[utoipa::path]`s in an `OpenApiRouter` nested at `/api/v1`, with catch-alls (problem 404), a 405 fallback with `Allow`, catch-panic (problem 500) and `no-store`; `build_site` merges it before the public fallback.
- F15: `Store(ForeignKey)` → 409 `conflict` ("a related record changed; retry").
- F16: core gains actor-checked reads for terms, menus, settings, types and taxonomies; handlers only translate.
- F17: a type whose `fields` has no `fields` member is schemaless (built-ins, seed, plugins keep working); `featured_image` (UUID string or null) is always allowed.
- F18: `ferrite_core::permalink::rules_from` (later split into `stored_rules` + `check_registered`) is the one loader inside the `Tx`; the binary delegates to it.
- F19: `q` with `author`, `term` or `parent` is 422; with `q` the order is relevance; empty `statuses` = the five non-trash statuses.
- F20: PATCH `parent_id` is a double option (`null` = top level); absent `excerpt` keeps, `null` re-derives.
- F21: type `media` is 404 under `/content/{type}` (uploads are `/media`, M2a-2).
- F22: a delete with `reassign_to` also emits `user:<reassign_to>`.
- F23: allowlisted settings are written with `autoload = true`.
- F24: `RedirectService::update` to a source another row holds (either slash variant) is `Invalid("source taken")`.
- F25: redirect import: duplicate sources are line errors; loop/chain checks run in memory over a pre-read plus the file; the write `Tx` only upserts and emits (a concurrent manual edit can still close a loop, M1c-1 P2).
- F26: a new type or taxonomy name used by an existing top-level item slug is refused.
- F27: `Route::Preview` is dispatched right after health and assets, before redirect rows and the cache; `_preview` is in `EXACT_ONLY`.
- F28: keep the `--login` flag, the conditional `Secure` (P7) and an `init` without users; 07 §2 and 09 §8 corrected in Task 14.
- F29: the real-binary tests and the curl session send `Origin: <site.url origin>`; the cluster harness sets one site key.
- F30: `init` creates `secret.key` only for a solo config without `auth.secret_key`; otherwise the first solo `serve` creates it.
- F31: the 50-token cap is check-then-insert, accepted as a soft cap; as built the count runs after locking the owner's row (`get_for_update`), so concurrent creates for one user serialize and the cap holds.

## Controller rulings

- Ruling R1: P4 accepted: cluster mode requires a configured `auth.secret_key`; solo generates `secret.key` in the data folder — a database dump must not carry the key that unseals TOTP and plugin secrets — cost: one more required setting for cluster operators (an `auto`-mode Postgres + S3 site now needs it too).
- Ruling R2: P3 accepted: passkeys deferred past M2 — `webauthn-rs`'s newest release is a pre-release; the ROADMAP already listed passkeys as a stretch — cost: as P3.
- Ruling R3: P14 accepted: logins are immutable, the display name stays editable — WordPress also forbids login changes and it keeps `/author/<login>/` stable — cost: a user who wants a new login needs a new account.
- Ruling R4: pre-flight findings F1–F31 accepted as proposed, binding for implementers and reviewers — they resolve plan-text errors against the code and spec — cost if wrong: a fix round in the owning task.
- Ruling R5: an `audit_log (actor_id)` index inside the unreleased `0005` (no new migration) — user delete and reassign scan by actor — cost: one index write per audit row.
- Ruling R6: user-agent truncation to 256 characters and calling `RateLimitRepo::hit` outside transactions are core obligations (Task 5) — Postgres `now()` is the transaction start inside a `Tx`, and the bucket's row lock would be held until commit — cost: none.
- Ruling R7: the rate-limit window is monotonic: the upsert keeps the newer window (`GREATEST`/`max`) and resets the count only when the incoming window is newer; a late older-window hit counts in the current window — an unconditional overwrite lets a late commit reset the bucket — cost: a stale hit counts once more.
- Ruling R8: accepted: reassign bumps `version` (not `updated_at`; an author change is not an edit), `revisions_author_idx` in 0005, `update` no longer writes `totp_secret` (F4), `advance_totp_step` is `Ok(false)` for an unknown user — consistent with optimistic locking and F4 — cost: none.
- Ruling R9: accepted: fallible key generation and sealing (`CoreError::Random` → 500), infallible HMAC keying with RFC 2104 zero padding (proven equal to `new_from_slice`), uppercase hex accepted in the site key; 09 §8 documents that a cluster `init` needs `FERRITE_AUTH__SECRET_KEY` — the OS generator can fail; uppercase keys are the same key — cost: none. (Zeroization of key material was parked from the Task 3 review; ROADMAP M2a-2.)
- Ruling R10: a self-patch carrying the current role or status is a no-op (a different value stays `Invalid`), and delete-with-reassign locks the two user rows in id order — admin forms send whole objects; mutual reassigns must serialize instead of deadlocking — cost: none.
- Ruling R11: the current-password checks of a self password change go through the per-login rate-limit bucket — otherwise a stolen session or a `users:write` token can guess the password at argon2 speed — cost: a user who mistypes often is limited like a login.
- Ruling R12: box the large `LoginOutcome` variant (no lint suppression); set `last_login_at` only after full authentication (after TOTP); `create_token` refuses scopes the actor lacks; TOTP confirm codes go through the per-user `totp:user` bucket in core (`totp_disable`, which checks only the password, uses the per-login bucket instead, accepted in the fix round as consistent with R11); expired-token cleanup joins `sessions.prune` — 6-digit codes are guessable, and a failed second factor is not a login — cost: none.
- Ruling R13: accepted: `serde_path_to_error` as a direct dependency (already transitive via axum), boxed `Problem.current`, fallible `ApiState::new`, the API's own test fixture, `/api` → 301 `/api/` (public rules outside `/api/v1`); `meta.version` is `CARGO_PKG_VERSION`; the option autoload cache must refresh on `options.changed` on every node — same binary, same version; cluster staleness otherwise — cost: none.
- Ruling R14: accepted: `AuthService::change_password` (R11); a password change revokes every session and issues a new cookie (F12); bearer logout → 400 `bad-request`; `WWW-Authenticate: Bearer` on every 401; the harness `ClientIp` fix; every HTTP self password change goes through `change_password` — RFC 9110 requires a challenge; one throttled path — cost: none.
- Ruling R15: TOTP enrollment (confirm) requires the current password, checked through the login bucket — a stolen session alone must not enroll another authenticator — cost: one more field in the confirm request. Parked to M2a-2: the `__Host-` prefix for the session cookie on `https` sites (cookie tossing).
- Ruling R16: accepted Task 8 deviations (the `UNIQUE_FIELDS` table is the shared pattern for later tasks); terms read outside the `Tx` on PATCH accepted (a rare, retryable 422); an absent excerpt on a body change re-derives a derived excerpt — keep one mapping table; a manual excerpt must survive — cost: none.
- Ruling R17: core `can_read(actor, item)`: published (publicly visible) items, own items, or `edit_others` (editor, admin); it gates single reads, revisions and the 412 `current` body, and filters lists, cursors, counts and `q` in SQL — contributors reading others' drafts contradicts previews and WordPress — cost: editors' list views need the capability they already hold.
- Ruling R18: unknown taxonomy → 404; the render re-resolves the route after the flush guard (a real pre-existing race, tested); a same-name create race must not persist duplicates (fixed in review with R19); term archives for custom types go to the ROADMAP (M2a-2) — a clean conflict for the loser is fine, two rows are not — cost: none.
- Ruling R19: type and taxonomy writes run under the named lock `types`; `permalink.*` option writes take the same lock — the cross-table name and permalink checks are not serialized otherwise, and `serve` refuses to boot on an invalid combination — cost: type, taxonomy and permalink writes serialize site-wide (30 s wait, then 503).
- Ruling R20: accepted: store-wins option reload (`updated_at` comes from the writer node's clock), the Task 10 deviations, CSV formula neutralising with `'`, and the P2 loop race (the server resolves one hop per request, so a raced loop shows only as a browser redirect loop until an admin fixes it) — cost: an uncached key until its next event when reloads overlap.
- Ruling R21: redirect sources under router-owned paths (`slug::RESERVED` or a leading `_` in the first segment) are refused on write — such a row could never be reached or would shadow core routes — cost: a legacy redirect under `/feed/…` cannot be re-saved (stored rows still resolve).
- Ruling R22: `ferrite user reset-password` keeps API tokens (independent credentials, like WordPress application passwords); disabling a user already blocks both — tokens are revoked individually — cost: a compromised account's tokens survive a password reset until revoked; documented in 07 §2 and 09 §8.
- Ruling R23: accepted Task 12 concerns: logged-in responses are `private, no-store` (a CDN can only serve logged-in users the anonymous view); 06 §3 wording checked in Task 14; `can_read`'s "published" means publicly visible now (status published and `published_at <= now`), on both backends and in the API — a future-dated item must stay hidden from non-authors without `edit_others` — cost: none.
- Ruling R24: accepted Task 13: no index on `api_tokens.expires_at` (≤ 50 tokens per user, hourly prune); the ≈200-line serve-harness duplication in `crates/ferrite/tests/api.rs` goes to the final review (a shared dev-dependency test-support crate is the likely fix, without `allow(dead_code)`); per-table prune budget slices (80 s each of 240 s) — a sessions backlog must not starve tokens and rate limits — cost: a full scan of `api_tokens` per prune.
- Ruling R25: keep the built problem slugs `precondition-failed` (412) and `busy` (503), superseding P10's `version-conflict` and `unavailable`; zeroization of key material and passwords is listed under M2a-2 (it was "M4 hardening" in the Task 3 note) — the slugs name the HTTP condition and no client exists yet — cost: none.
- Ruling R26 (final review): (I1) the client address keys the per-IP login and token limits, so behind a reverse proxy missing from `server.trusted_proxies` they are one bucket for the whole site: documented in 07 §2, 09 §5 and `client.rs`, and `X-Forwarded-For` from an untrusted peer logs a warning once per peer address (first 64 peers per process); (I2) reading revisions needs a role that may edit the item (`role_can_edit`, the role half of `can_edit`; a `content:read` token of such a role still reads them), narrowing R17 for revisions only (WordPress requires `edit_post` on the parent); (M1) `must_reset` restricts sessions only, API tokens keep working (R22); (M2) TOTP confirm deletes the user's other sessions in the same `Tx`, keeping the caller's (through a token every session ends); (M3) declined: reading oneself needs no scope (R10); (M4) creating a redirect source whose trailing-slash variant is stored is refused on create and import, as update does (F24), while a stored pair still upserts in place; (M5) `sitemap-*.xml` first segments are router-owned redirect sources; (M6) the `OptionService` autoload cache had no reader in `serve`, so the cache, its reloader wiring and its tests were removed (reintroduce with the first reader, ROADMAP M2a-2, with R13's refresh on `options.changed`); (M7) an OpenAPI-driven sweep test: every unsafe operation but the two logins is `401` without credentials and `403 csrf` for a cookie without the token; (M8) `crates/ferrite/tests/serve.rs` and `tests/api.rs` merged into one `tests/serve/` binary with one harness (supersedes R24's test-support crate idea) — revision history holds removed text; a misconfigured proxy is the default deployment's failure mode; a stolen session must end when the user enrolls TOTP — cost: contributors and authors no longer read revisions of others' published posts or their own published posts (contributors), and `OptionService` has no cache until M2a-2.

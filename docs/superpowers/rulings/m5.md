# M5 AI assistants (MCP) — controller rulings

Decisions made while executing the M5 plan (docs/superpowers/plans/2026-11-01-m5-mcp.md,
subagent-driven; spec docs/design/12-mcp.md). Format: ruling — reason — cost if wrong.
R-m = controller rulings, numbered in the order they were made. Where the code differs
from a ruling's text, the line says "as built".

## Rulings

- R-m1 (Task 1): migration `0013_oauth` is not marked lossy — grants and codes are
  re-creatable credentials, like sessions, and the rollback tests assume the newest
  migration is not lossy — cost if wrong: users reconnect their assistants after a schema
  rollback.
- R-m2 (Task 1): `ApiTokenRepo::delete` may delete an OAuth access token by id — it only
  revokes that token — cost: none.
- R-m3 (Task 1): interface deviations accepted: `take_code` stamps the grant id on the
  code, `rotate_grant` is a compare-and-set returning `bool`, `prune_expired(now, limit)`.
- R-m4 (Task 1): refresh-token replay detection is one rotation deep (spec §4): only the
  previous hash is kept, so a token two rotations old is merely unknown.
- R-m5 (Task 1): connecting the same client again replaces the user's earlier grant for
  it, so a user's grants are bounded by the clients and need no paging. As built: the
  replacement happens at the code exchange (`OAuthService::exchange`).
- R-m6 (Task 1): pruning unused OAuth clients goes to the later list.
- R-m7 (Task 2): spec §7's "request bound to the user who opened it" is dropped — a
  request is single use and approval needs a session and its CSRF token — cost: an
  attacker who gets a victim to open a consent link still needs the victim to choose
  Approve (the usual OAuth phishing exposure).
- R-m8 (Task 2): `/oauth/authorize` gets a per-IP limit (`oauth:authorize:ip`, 30 a
  minute) against metadata-fetch amplification.
- R-m9 (Task 2): a grant's `last_used_at` (and its 30-day expiry) moves on refresh only,
  not on every tool call — at most an hour stale, since access tokens last an hour —
  accepted.
- R-m10 (Task 2): deviations accepted if correct: `Arc<AuthService>`,
  `AuthorizeError::Server`, a boxed redirect URI, extra `OAuthError` variants, `get_grant`,
  `redirect_uri` required at the token endpoint, the prune slice.
- R-m11 (Task 2 minors, folded into Task 3): the consent screen's redirect host shows the
  scheme for a non-http(s) URI; deny needs `users:write` like approve; format (`Cf`)
  characters are stripped from client names. Revoking an already rotated refresh token is
  not special-cased (RFC 7009 allows it).
- R-m12 (Task 2): the issuer is `site.url` as configured, path kept; the authorization
  server metadata is served at `/.well-known/oauth-authorization-server` and, when
  `site.url` has a path, also at the RFC 8414 path-inserted address.
- R-m13 (Task 3): deviations accepted: the grants list answers `{items}`; a bearer token
  on the consent routes is `403`; the grant routes stay live while `mcp.enabled` is off
  (users can still disconnect); `/oauth/revoke` answers `400` to a missing token and has a
  30-a-minute per-IP limit; the error page sends `frame-ancestors 'none'`.
- R-m14 (Task 3): the root protected-resource document names `<site>/mcp` — clients look
  up the document for the URL they connected to — cost: a strict RFC 9728 client that
  probes the root could see a mismatch; acceptable.
- R-m15 (Task 4): embeds and other blocks Markdown cannot express stay as `ferrite-block`
  fences (a lossless round trip); spec §5.3 amended.
- R-m16 (Task 4, for Task 6): with no `title`, a leading `# H1` becomes the title; with a
  title equal to the H1 (trimmed, case-insensitive) the H1 is dropped; a different H1 is a
  tool error asking to move it to `title` or make it `##`.
- R-m17 (Task 5): accepted: the per-user rate limit is counted once in `call_tool`;
  `GET`, `PUT` and `DELETE` answer `405` before authentication; rmcp's Host allowlist is
  off (its default is loopback only; the Origin check and the bearer token cover DNS
  rebinding); the cancellation token is not wired (JSON responses, axum's graceful
  drain); `site_search` pages with a cursor (spec §5.1 amended); `site_overview` lists the
  sections the caller cannot read under `unavailable`.
- R-m18 (Task 5): when the audit append fails after a committed write, the tool logs a
  warning and still returns success (the model must never retry a done write) — cost: such
  a write can go unaudited; recorded in the exit's limits.
- R-m19 (Task 6): a preview link needs the person's admin session (no signed expiring
  links) — cost: a model cannot fetch the preview itself.
- R-m20 (Task 6): `fields` merge per member and `null` clears a member; status changes go
  only through the lifecycle tools.
- R-m21 (Task 6): the content resource's front matter is TOML between `+++` lines, as the
  Markdown importer reads it.
- R-m22 (Task 7): the `/mcp` body limit is 9 MiB (a 6 MiB file as base64 plus the JSON
  envelope); spec §2 amended. As built (final fix pass): structured values a tool writes
  (`body_blocks`, `fields`, menu items, settings maps) are still refused above the REST
  API's 4 MiB JSON cap.
- R-m23 (Task 7): `404` versus `403` on term and redirect writes matches REST; `menu_set`
  takes the nested tree; terms list with page and total; `content_type_update` is
  destructive.
- R-m24 (Task 7 review): media URL fetches get their own semaphore (2 per node), outside
  the upload slot; `null` keeps its REST meaning per tool (the descriptions say so).
- R-m25 (Task 8): settings tools take free-form `changes` (core validates); `UserOut`
  keeps the e-mail, as the REST admin view does; the `comment_reply` path without an IP is
  untested (every request has a client IP).
- R-m26 (Task 9): the `ConsentRedirectDto` rename (an OpenAPI name clash) is accepted;
  OAuth access tokens are excluded from the personal token list by the store; the consent
  levels are Off / Read / Write; the `must_reset` → consent path and Firefox/WebKit runs
  are exit gates.
- R-m27 (Task 10): pages that promote MCP carry "Coming in the next release (0.2.0); build
  from source today" until a release ships it (a ROADMAP item); the release itself is the
  user's decision.

## Final review fix pass (2026-11-02)

- R-m28: disabling a user ends their OAuth grants in the same transaction, one
  `oauth.disconnect` audit row per grant with reason `user_disabled`, so re-enabling the
  user revives no connection (spec §3.2).
- R-m29: OAuth access tokens are `fera_…`, personal tokens `fer_…`, and `resolve_token`
  requires the prefix to match the row (`fera_` only with a grant) — a node older than M5
  looks up only `fer_` values and knows no grants, so a mixed-version cluster or a binary
  rollback would otherwise accept OAuth tokens on `/api/v1` (spec §3.1).
- R-m30: an OAuth grant can never hold `users:write`, `import:write` or `system:write`
  (no MCP tool uses them); `scopes_supported` lists the 19 grantable scopes (spec §3.3) —
  defence in depth.
- R-m31: at most 4 client metadata fetches run at once per node; one more uses a cached
  copy (up to 7 days old) or answers a `503` "busy, try again" page, never a redirect.
- R-m32: deferred to the later list: grouped counts, terms paging in the store,
  media-kind field references, a sanitisation end-to-end test through MCP and bad-cursor
  tests, client pruning (R-m6).

## Client documentation read on 2026-11-02

The notes the guide's client steps were written from (checked 2026-11-02 by web search;
the guide keeps the wording generic where a client's menus move, and does not name Claude
Code's sign-in button, which was not run interactively):

- Claude (claude.ai, Claude Desktop, Cowork): custom connectors with remote MCP, all
  plans including Free (beta). Add custom connector → server URL → Connect; OAuth sign-in;
  optional Advanced settings for a client id and secret (left empty, the client registers
  itself). Connections originate from Anthropic's cloud, so the site must be on public
  HTTPS. Team/Enterprise: an Owner adds the connector. Sources:
  <https://support.claude.com/en/articles/11175166>,
  <https://claude.com/docs/connectors/custom>.
- ChatGPT: Settings → Connectors/Apps → Advanced → Developer mode; create a connector
  with the MCP URL and Authentication "OAuth". Remote only (cloud). Plan availability
  varies (Pro/Team/Enterprise/Edu; Plus per some). Source:
  <https://auth0.com/blog/add-remote-mcp-server-chatgpt/> (OpenAI's own docs not checked;
  its developer-mode page answered 404 when fetched).
- Claude Code: `claude mcp add --transport http <name> <url>`; then `/mcp` → select the
  server → Authenticate (browser); or `--header "Authorization: Bearer <token>"`.
  `--scope project` writes `.mcp.json`. Runs locally, so it works with `http://localhost`
  sites.
- VS Code: `.vscode/mcp.json` `{"servers": {"ferrite": {"type": "http", "url": "<url>"}}}`;
  an OAuth browser flow on the first connection; tokens through `${input:...}` with
  headers. Source: <https://code.visualstudio.com/docs/copilot/reference/mcp-configuration>.
- Cursor: `~/.cursor/mcp.json` or `.cursor/mcp.json`
  `{"mcpServers": {"ferrite": {"url": "<url>"}}}`; OAuth in the browser; headers for static
  tokens. Third-party sources only at first; Cursor's own page
  (<https://cursor.com/docs/context/mcp>) was read for the guide (site/VERIFIED.md).

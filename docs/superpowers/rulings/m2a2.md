# M2a-2a extensions and the plugin platform — plan and controller rulings

Decisions made while planning and executing docs/superpowers/plans/2026-10-24-m2a2-extensions.md (subagent-driven). Format: ruling — reason — cost if wrong. P = plan rulings, F = pre-flight findings (all accepted as proposed by R3; one line each), R = controller rulings during execution. Where the code differs from a plan ruling's text, the line says "as built".

## Plan rulings

- Plan ruling P1: M2a-2 is split in two: M2a-2a (this plan, 14 tasks: extensions and the plugin platform) and M2a-2b (media, comments, system API, hardening, the remaining deferred and parked items) — the extension and plugin items share the install flow, grants and host changes, while media, comments and system share uploads and the new migration; one plan would be ~26 tasks — cost: one more plan/review cycle.
- Plan ruling P2: no migration in M2a-2a: grants with approved limits live in `plugins.granted` (versioned JSON, the bare M1c-2 form still read), settings in `options`, limits in `rate_limits`, actions and purges in `jobs`; `0006` (same name on both backends, `.down.sql`, expand-only) is M2a-2b's (idempotency keys, the sanitised-SVG marker) — the existing tables hold everything — cost: none.
- Plan ruling P3: approval is a fingerprint of what the admin saw: `POST /plugins/inspect` returns the report and `fingerprint` = SHA-256 over plugin, version, artifact hash and the grant; `POST /plugins` must carry it; the stored `granted` is always an object (closes M1c-2 R21's open item) — a grant cannot be approved for different bytes — cost: the upload is sent twice (inspect, install). As built the plugin name `inspect` is reserved (R9).
- Plan ruling P4: widening updates need the new approval in the same request; nothing is stored unapproved — design 05 §2's "stored but not activated" needed a pending-version column and a second approval endpoint, while with P3 every install shows the diff (`report.added`) and an update without the matching fingerprint is refused while the old version keeps running — cost: no "approve later" queue.
- Plan ruling P5: limits above host defaults are approved per plugin, up to ceilings (memory ≤ 256 MiB, fuel ≤ 10 × default); above the default needs approval (a high-risk report line), stored in `granted.limits` and applied by `prepare_with`; above a ceiling is refused at inspection (closes M2a P28) — plugins with real workloads need more than the defaults — cost: worst-case memory per call grows for approved plugins (still capped by P22's call count). As built a pooling host's memory ceiling is its default (its slot size), so a report never offers what the node cannot load.
- Plan ruling P6: the permission report lives in `ferrite-plugin-host` next to the manifest it describes; plain-language lines and high-risk flags — one place knows what a capability means — cost: report wording changes need a host release.
- Plan ruling P7: bare IP addresses and `localhost` are refused in `capabilities.http`; the post-resolution SSRF check comes with the real `http` import (M2a-2b) — an allowlist entry should name a host, and the stub import makes no request yet — cost: a plugin cannot target an IP-only API. As built (F5, R7) also refused: names without a dot, a last label of digits, labels starting `0x`, a first label starting `localhost`; hosts are lowercased with a trailing dot dropped.
- Plan ruling P8: the install pipeline moves to `ferrite_http::extensions::Installer` (library, `thiserror`), used by the API and the CLI; `ExtensionService` stays the system path and `ExtensionAdmin` is its actor-checked facade with audit rows (closes M1.5 R11); compiles run on the blocking pool, two at a time per node, on one scratch host that never commits — one pipeline for both callers — cost: none. As built one `Installer` per node also bounds uploads in flight to four (`UPLOAD_SLOTS`, else `503 busy`).
- Plan ruling P9: plugin delete keeps KV and settings 30 days: the row goes in one `Tx` with `plugins.changed` and a `plugin.purge` job due in 30 days (keyed by deletion time; a reinstall in between keeps the data); `purge=true` deletes at once; no retention table — WordPress-like, and an accidental delete is recoverable — cost: a reinstalled plugin sees its old data. As built (F13–F16, R5) the deletion marker option `plugin.<name>.deleted_at` decides, `purge=true` purges after the commit and its job sweeps again 2 minutes later, and a daily `plugin.purge_sweep` re-enqueues overdue purges.
- Plan ruling P10: extension reads need the role capability and `extensions:read` (`require_reader`) — only admins may see installed plugins and their grants — cost: editors see no plugin list.
- Plan ruling P11: upload formats: themes are the raw deterministic ustar bundle (`application/x-tar`, M1.5 P17) as the request body; plugins are `multipart/form-data` (`manifest`, `component`, `approve`) through axum's `multipart` feature (multer 3.1.0); per-route `DefaultBodyLimit`; `Idempotency-Key` stays with media uploads (M2a-2b), where retries create rows — no new format for themes, and the plugin parts need names — cost: none.
- Plan ruling P12: activation refuses a theme that does not load (fetched, hash-checked, unpacked and compiled before the row changes); an embedded theme without a row is installed from the embedded files when activated; a startup fallback is flagged as `nodes.meta.theme.fallback` and shown by `GET /themes` — an admin must not brick the site — cost: activation takes as long as one theme load. As built (F12, R8) `fallback` is true whenever a node does not serve the active row's artifact (also after a failed hot swap).
- Plan ruling P13: one settings schema for themes and plugins (`ferrite_core::ext_settings`, 05 §4c), validated in core against the schema of the installed manifest; theme settings stay one object option, plugin settings one option per key; `secret` is plugin-only, sealed with the site key per plugin and key, write-only in the API, opened only by the owning plugin's `settings.get`; `settings.get` answers declared keys only and falls back to the declared default — one validator, and secrets reach only their owner — cost: a lost site key makes stored plugin secrets unreadable (admins re-enter them). As built (R11) a stored value that no longer fits its definition reads as the default and is listed as `invalid` by the API.
- Plan ruling P14: the per-node option cache is not reintroduced (to M4): theme settings and `site.*` are read on page-cache misses only and plugin settings per plugin call, each one primary-key read — a cache adds cross-node staleness (M2a R13's refresh) for no measured gain — cost: one indexed read per setting on misses.
- Plan ruling P15: plugin routes: `/_p/{plugin}/{*path}` is mounted before the public fallback for every method; exact path and method from `[routes]`; request headers allowlisted, body ≤ 1 MiB; the response keeps only status, `Content-Type`, `Content-Language` and a root-relative `Location` on 3xx and always gets `Content-Security-Policy: sandbox allow-forms`, `nosniff`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`; never cached; never `Set-Cookie`; the visitor's user id comes from the session cookie only; `client-ip-hash` is per plugin (HMAC with the plugin name) — a hostile route must not reach the visitor's session or join visitors across plugins — cost: plugins cannot set caching headers or cookies. As built the CSP also has `form-action 'self'` (R14), `/_p/{plugin}/` serves a route `"/"` (F25), and a request without a known client address is `503`.
- Plan ruling P16: route rate limits are DB-backed fixed windows through `AuthService::hit_limit` (bucket per plugin, route and client /64), so they hold across nodes; the API's origin rule guards non-GET/HEAD unless `cross_origin` — a flood must be cut on every node — cost: one upsert per route request. As built the bucket names the route by a 32-hex hash of its path (F24).
- Plan ruling P17: mail: `[mail] smtp_url[_file]` + `from`, lettre 0.11.23 (rustls/ring/webpki-roots, matching the binary's ring provider); a `Mailer` trait in core so services and tests use `MemoryMailer`; without `[mail]` the import errors and the reset endpoint is `503 mail-unavailable` — one transport, testable without SMTP — cost: no other transports (sendmail, API providers) yet. As built every send goes through the node's `MailQueue` (R15) and credentials need TLS or a loopback relay (R16).
- Plan ruling P18: `notify-admins` bounds: active admins only (≤ 50), one mail per call, 10 per plugin per hour (shared bucket), subject ≤ 200 characters without control characters, body ≤ 64 KiB, a site-title prefix and a "sent by plugin" footer; refused on the render path (M1c-2 R20) — a plugin must not spam or reach arbitrary recipients — cost: chatty plugins hit the cap. As built the admins are in `Bcc` (F29).
- Plan ruling P19: password reset tokens are stateless and single-use: sealed `{user, exp 1 h, fingerprint of the current password hash}`, so any password change (the reset included) kills them; the request always answers `202` and mails from a background task so timing does not reveal accounts; limits 5/min per IP and 3/h per account input; the link puts the token in the URL fragment (`/admin/reset-password#token=…`) so it stays out of logs and `Referer`; the reset ends sessions, keeps API tokens (M2a R22) and does not bypass TOTP — no reset table, no enumeration — cost: a mail failure is only logged (the user retries).
- Plan ruling P20: action hooks are enqueued by core in the write transaction: subscribers are read from the enabled `plugins` rows' manifests inside the `Tx`, so an event is never lost or sent for a rolled-back write; one job per (plugin, event); the binary's handler dispatches through the node's host with one registry snapshot per call (M1.5 R13 holds by construction) — transactional delivery — cost: one `plugins` read per content save. As built the read is one narrow SQL query (`PluginRepo::action_subscribers`) and action jobs run at priority -1.
- Plan ruling P21: `request.served` is buffered per node and flushed every 10 s or 1 000 events into one job per subscribed loaded plugin (05 §4a), including cache hits; no IP, cookie or full user agent; at most 10 000 events buffered; lost on a crash — analytics without a write per request — cost: analytics can lose up to 10 s per crash.
- Plan ruling P22: plugin calls get a per-host concurrency cap and a per-render time budget (closes the M0 review items); a call that cannot get a permit within its deadline is skipped without counting as a plugin failure (load, not misbehaviour); a page's filters share `plugins.render_budget_ms` — bounded memory and page latency under load — cost: under load filters are skipped (pages volatile) rather than queued. As built (R20) action jobs get `min(cluster.workers − 1, cap)` slots and a busy action is released with its attempt refunded.
- Plan ruling P23: `meta` is type-scoped to the plugin's `content.read` types, and `"*"` meta grants never reach other plugins' `plugin.<other>.*` keys (closes the M0 follow-up); the `meta-writer` fixture declares `content.read = ["post"]` — a meta grant must not reach every type or another plugin's data — cost: a meta-only plugin must also declare the types it annotates. As built (R20(1)) `meta.set` also refuses items the plugin cannot read (drafts).
- Plan ruling P24: new test plugins `router`, `notifier`, `counter`, `hello-v2`; hostile `route-xss`, `route-flood`, `mail-flood` — CLAUDE.md requires hostile plugins for host changes — cost: longer plugin builds in tests. As built `settings-probe` was added too (R11).
- Plan ruling P25: deferred to M2a-2b: media service and uploads (`media.variants`, semaphore, `put_stream` limits, `Idempotency-Key`, SVG sanitising), comments, the system API (status, nodes, jobs list/retry, `GET /plugins/{name}/metrics`, metrics summary, audit list), the ammonia URL allowlist, the real `http` import, the `__Host-` cookie prefix, key-material zeroization, term archives for custom types and the "Deferred from M1c-2" backend items; to M4: the option cache (P14) — scope — cost: listed in the roadmap.
- Plan ruling P26: the extension CLI is an operator path (M2a P17): no actor; `plugin install` prints the report and needs `--yes` or an interactive `y`, and approves exactly what it printed; SQLite commands fail while `serve` holds the data-folder lock — operators need a way in without the API — cost: as `ferrite user`. As built the read-only report command is `ferrite plugin check`.
- Plan ruling P27: one new problem slug, `mail-unavailable` (503); approval mismatches are `422 validation` with `errors[0].field = "approve"`; `/_p/` errors are plain text because they are the plugin's surface, not the API's — reuse the M2a-1 slugs — cost: none.
- Plan ruling P28: the sweep's unauthenticated list grows by the two password-reset endpoints only; both check the origin like login (`SameOrigin`) — every other unsafe route needs credentials — cost: none.
- Plan ruling P29: actions on removed or disabled plugins are dropped, not retried; a plugin not yet loaded on the claiming node (an enable racing the reload) is retried with the usual backoff — a disabled plugin must not run later — cost: an action enqueued just before a disable is lost (intended).
- Plan ruling P30: theme deletion is not built (not in 07 §1's table); an installed theme row stays until M4's `artifacts.gc`/cleanup work — scope — cost: unused theme artifacts stay stored.

## Pre-flight findings (accepted by R3)

- F1: incomplete Files lists (test-module registrations, `sha2` and `async-trait` deps, every `ApiParts` and `ExtensionAdmin::new` site, `slow-import`, `crates/ferrite/tests/serve/`) are in scope of the owning task.
- F2: `permission_report` takes `artifact: &str` (64 lowercase hex), so the host needs no domain type for it.
- F3: the report test of the design example is a unit test in `src/report.rs` using `DESIGN_EXAMPLE`.
- F4: `content.meta.read` and `content.meta.write` are separate report items; read is high risk only for `"*"`, write for anything outside `plugin.<name>.*`.
- F5: the bare-host rule also refuses a host with no dot, an all-digit last label and labels starting `0x`.
- F6: `manifest_from_json` moves into the host as `Manifest::from_json`; `Grant::to_json` writes only non-default members; `from_json(to_json(of(m)))` covers `m`.
- F7: a unit test pins one fingerprint, so a dependency enabling serde_json `preserve_order` fails loudly.
- F8: `install_plugin_file_uses_the_site_limits` is rewritten: above the site default and ≤ ceiling loads with `granted.limits` recorded; above the ceiling is refused.
- F9: a null legacy grant is reported against `Grant::of(<row manifest>)` (as built `Grant::legacy`, R7).
- F10: theme rows are written with `"settings": []`; a row without an array reads as "schema unknown" and falls back per F22.
- F11: theme failures about the stored or sent bytes (`HashMismatch`, `Theme`, `NameMismatch`, `TooLarge`, media `NotFound`) are `422 validation`; other media errors 500; the CLI exits 1 for all.
- F12: `fallback = true` whenever the served theme is not the active row's artifact; `false` when it is, or when no row is active and embedded `blog` serves.
- F13: the shared delete helper enqueues `plugin.purge` for both the API and the CLI path.
- F14: the delete `Tx` writes the marker option `plugin.<name>.deleted_at`; a purge runs only when no row exists and the marker equals the job's `deleted_at`.
- F15: `purge_plugin_data` holds the `extensions` lock across the check, the KV batches and the settings `Tx`; `Busy` retries the job.
- F16: the delete `Tx` always enqueues the purge job (with `purge` due at once, as built 2 minutes later, R5; else +30 d); the immediate purge is an optimisation.
- F17: the binary purge test enqueues `plugin_purge_job` with `run_at` overridden to now.
- F18: API tests assert the event row and then reload themselves; the event-driven path stays covered by `crates/ferrite/tests/serve` and `cluster/reload.rs`.
- F19: `plugins/examples/hello-v2` is a manifest-only `0.2.0` (adds `kv`) used with `hello`'s component.
- F20: `nodes` in plugin and theme DTOs lists only nodes with a heartbeat in the last 30 s.
- F21: with no active row, embedded `blog` is listed `active: true, origin: "embedded"`; `DEFAULT_THEME` moves to `ferrite_theme`.
- F22: the theme settings schema is the row's `manifest.settings`, else the row's artifact's manifest, else the embedded theme when there is no row; never `AppState`.
- F23: plugin `[settings]` keys are `[a-z0-9_-]{1,64}`.
- F24: the route rate-limit bucket names the route by 32 hex of SHA-256 of its path.
- F25: `/_p/{plugin}/` is also mounted (route `"/"`); `AppState` derives the site origin once with `api::state::origin_of`.
- F26: `route-xss` reports the request header names it received in its body.
- F27: the two-node flood test aligns to a window boundary and gives a second client through `X-Forwarded-For` with `trusted_proxies`.
- F28: `notify_admins` does every check synchronously, then hands the send to a background task and returns `Ok`; send failures are logged.
- F29: `notify-admins` order: render-path refusal, per-call, subject/body checks, hourly hit; one message `To: <from>` with the admins in `Bcc`; the subject prefix is the config site title fixed at boot.
- F30: `ferrite-config` checks `smtp_url` and `from` by shape (`url::Url`); `SmtpMailer::new` parses both with lettre at `serve` boot.
- F31: reset confirm hashes first, then in one `Tx` locks the user row, compares the fingerprint there, writes, deletes sessions and writes one `user.password_reset` audit row.
- F32: `MemoryMailer::wait_for(n, timeout)` for tests of mail sent from background tasks.
- F33: the reset link targets `/admin/reset-password`, which 404s until the M2b SPA; 07 §2 documents posting the token to `POST /auth/password-reset/confirm`.
- F34: `slow-import` gains a `post.saved` action; the hot-swap and cap tests run at host level with gated services; three manifest names `slow-a/b/c`.
- F35: `NotSubscribed` → done (logged); `Disabled` with the row enabled → retry; `Busy` → retry.
- F36: `request.served` paths are the raw percent-encoded path without query, cut to 512 bytes; `referrer_host` is the lowercased ASCII host (≤ 253) or null.
- F37: with a budget the hard deadline is `min(1.5 × deadline, until − now)`, and waiting for a permit counts against it.
- F38: a new plugin is installed disabled (explicit enable); 05 §2 corrected in Task 14.

## Controller rulings

- Ruling R1: P4 accepted: an update needing wider grants is refused without the new approval fingerprint (the old version keeps running) instead of design 05 §2's stored-but-inactive version — no pending-version column, one approval path — cost: operators re-submit the update with approval.
- Ruling R2: P9 accepted: plugin delete keeps KV and settings 30 days (`plugin.purge` job) unless `purge`; a reinstall within 30 days gets its data back (WordPress-like) — documented in 05 §2 — cost: as P9.
- Ruling R3: pre-flight findings F1–F38 accepted as proposed, binding for implementers and reviewers — they resolve plan-text errors against the code — cost if wrong: a fix round in the owning task.
- Ruling R4: accepted Task 1: the deletion marker is cleared on reinstall, the audit detail shapes, `jobs::handlers(…, extensions)`; `ferrite plugin remove --purge` reuses the delete helper — consistent with F13–F16 — cost: none.
- Ruling R5: `purge=true` keeps the marker and the delete's job runs a second purge 2 minutes later (KV a node wrote before it reloaded); a daily `plugin.purge_sweep` re-enqueues stale markers — a purge must finish even after a failure or a dead job — cost: one more job per purge delete and one daily scan of `plugin.*` options.
- Ruling R6: route paths are not a grant: every route lives under the plugin's own `/_p/<plugin>/`, so a new path under an already-granted `routes` is not widening (the report still lists the routes); accepted Task 2 hardening: `localhost` labels, the 64 KiB manifest cap, the pooling memory ceiling = slot size — a path cannot reach anything outside the plugin's namespace — cost: an admin is not asked again for a new route path.
- Ruling R7: route `cross_origin` and `rate_limit` are part of the grant and fingerprint (relaxing one is widening; paths stay out per R6); a legacy null grant is `Grant::of(manifest)` with limits capped at the defaults until approved; hosts are canonicalised (lowercase, no trailing dot); a first label starting `localhost` is refused; the report's ceiling is the host's real ceiling; the DNS-rebinding resolved-address check stays in M2a-2b (P7) — an approval must cover what a route exposes — cost: a legacy `[capabilities]` grant with routes fails closed (no pre-M2a plugin has routes).
- Ruling R8: accepted Task 3: `ExtensionError::Task` → 500; a stored oversized artifact → 422; `load_theme_artifact` as a free function; `Arc<MediaStore>`; re-hashing at stage; a theme compile slot; fallback after any failed swap (consistent with F12) — cost: none.
- Ruling R9: the plugin name `inspect` is reserved (refused by `Manifest::parse`, like other reserved names) rather than documenting a 405 for `/plugins/inspect` — a plugin named `inspect` would shadow the route — cost: one name is unavailable.
- Ruling R10: activation is race-free: core `activate_theme` takes the expected artifact hash and answers `409 conflict` when the row changed under it; `ThemeNodeState` carries the node name and version like `PluginNodeState`; accepted: `201` without `Location` for theme uploads, `ExtensionAdmin::get_theme`, per-problem `errors[]`, the fallback flag lagging an activation by up to one heartbeat (10 s) — an activation must activate what was checked — cost: a concurrent replace makes one activation fail.
- Ruling R11: accepted Task 6: settings writes under the `extensions` lock, audit `{name, keys}`, the `settings-probe` test plugin; a stored value that fails the current schema (a type changed by an update) reads as the default and the settings view flags it, never reaching the guest — a secret or wrongly typed value must not leak through a schema change — cost: an admin re-enters type-changed settings. Recorded with it: `ferrite-plugin-host` depends on `ferrite-domain` for the shared setting rules (`SettingKind::setting_type` is the one public conversion).
- Ruling R12: accepted Task 7: the data-folder lock held during the install prompt (SQLite CLI runs only with `serve` stopped anyway), always-confirm install, `ExtensionService::remove_plugin` public; the flaky `ferrite-http` `plugin_read_errors_are_volatile::cluster` (one failure, then 3/3 passes) goes to the final review to diagnose — cost: none.
- Ruling R13: accepted Task 8 decisions provisionally, with the reviewer to check the per-request `plugins` row read and the unknown-IP bucket; as built a request without a known client address is `503` (one shared bucket would let one client exhaust it for everyone, or bypass the limit) and `is_enabled` reads one column after the origin and rate checks — cost: one indexed read per route request.
- Ruling R14: plugin route responses carry `Content-Security-Policy: sandbox allow-forms; form-action 'self'`: a sandboxed plugin page on the site's URL can only submit forms back to the site's origin, so it cannot be a credential-phishing form posting to another host (verified in Chrome and against CSP3; Firefox and Safari untested) — cost: a plugin page cannot post a form to an external service.
- Ruling R15: accepted Task 9: `OutgoingMail.bcc`; `MailQueue` (16 in flight per node, 10 s per send, cancelled at shutdown) as the only spawn point, enforced by type (`with_mailer(Arc<MailQueue>)`, F28); a `ferrite-http` → `ferrite-config` dependency; queue-full checked after the hourly hit — one bounded place where mail leaves the process — cost: a full queue drops mail (logged).
- Ruling R16: no opportunistic TLS for SMTP: URL credentials only with `smtps` or `tls=required`, except a plain-`smtp` loopback relay — lettre authenticates on whatever connection it has, so opportunistic mode could send the password in plaintext — cost: a plaintext relay on another host cannot take credentials.
- Ruling R17: accepted Task 10: `MailQueue` in `ApiState`, the shared `write_password` helper, TOTP kept on reset, API tokens kept (M2a R22), F33 documented; accepted concerns: a flood can fill the mail queue (dropped mail logged; the per-target and per-IP limits bound it), an unknown IP skips the IP bucket like login (`serve` always knows the peer), a store error is 500 regardless of the account. Carried to M2b: the reset page sends `Referrer-Policy: no-referrer` and strips the fragment from history — cost: none.
- Ruling R18: accepted Task 11 deviations; the `plugins` read inside every content and user write `Tx` is acceptable as one narrow indexed query of enabled rows' subscriptions (as built `PluginRepo::action_subscribers`); action `meta.set` scoping and the call cap covering action jobs carried to Task 13 — cost: one read per write.
- Ruling R19: accepted Task 12 scope and privacy decisions; the example `counter` plugin's lossy read-modify-write is an example limitation (at-least-once delivery), noted in its comments; an atomic KV increment import is a WIT change, so it needs a new world version and is deferred (ROADMAP "Later") — the v0.1 world stays unchanged — cost: plugin counters can lose increments.
- Ruling R20: Task 13: (1) `meta.set` keeps refusing items the plugin cannot read (a plugin that cannot read a draft has nothing to compute from; consistent with action visibility); (2) action jobs get `min(cluster.workers − 1, cap)` slots; (3) `Busy` and a full action slot must not consume attempts: the runner releases the job with the attempt refunded and a 1–5 s backoff, so bursts cannot push actions to `dead`; (4) budget cuts are skips, not failures (P22) — load must never disable or kill a healthy plugin's work — cost: a saturated node re-claims busy jobs every few seconds without limit.

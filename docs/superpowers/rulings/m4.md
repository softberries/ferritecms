# M4 ops and release — plan and controller rulings

Decisions made while planning and executing the M4 sub-plans (subagent-driven). M4-1:
docs/superpowers/plans/2026-10-29-m4-1-data-safety.md; M4-2:
docs/superpowers/plans/2026-10-30-m4-2-release.md. Format: ruling — reason — cost if wrong.
P = plan rulings (full text in the plan), R = controller rulings during execution. Where the code
differs from a ruling's text, the line says "as built".

## M4-1 plan rulings

- Plan ruling P1: export is a generic table dump over a static catalogue (`ferrite_store::catalogue::TABLES`, neutral per-column types), not domain DTOs — 34 tables, most without a list API, and a catalogue checked against the live schema cannot drift silently — cost if wrong: a wrong column type corrupts that column on a cross-backend copy (Tasks 2 and 3 guard it).
- Plan ruling P2: `sessions`, `rate_limits`, `events`, `nodes`, `idempotency_keys`, `plugin_failures`, all `jobs`, `search_docs`, `search_fts*` and `_sqlx_migrations` are skipped, `schema_meta` exports only `site_id`, search is rebuilt after loading — transient or derived data, and unfinished jobs carry node-local state that must not run twice — cost if wrong: a queued plugin action does not run on the copy; `media regenerate` repairs variant jobs.
- Plan ruling P3: the reader holds one read snapshot (Postgres `REPEATABLE READ READ ONLY`, SQLite one read transaction) behind `Store::export_reader()` with keyset paging — a live Postgres site exports consistently — cost if wrong: one long snapshot and some vacuum lag.
- Plan ruling P4: the loader (`Store::import_writer()`) runs the whole load in one write transaction, inserts self-references as NULL and fills them in `finish_table`, and writes exactly the archive's columns (each must be a catalogue column) — Postgres FKs are not deferrable, and atomicity makes a failed import retryable — cost if wrong: a large site holds one long transaction, and SQLite holds the writer for the whole load. As built (R6, R7, R8, R-pf1): a self-referencing row is held back until its parent is loaded and then inserted with the real parent (no NULL-then-update; `finish_table` and `commit` refuse a row still waiting for a parent that was not loaded); any failed call poisons the writer; the reader requires the source at the binary's latest schema and the loader writes exactly the columns present in each row.
- Plan ruling P5: `import-site` needs an initialised data folder with a fresh database (exported tables empty apart from migration-seeded types and taxonomies), migrates to the archive's schema version M (up from 0, down when newer, nothing when equal), loads, rebuilds search, writes `site_id`, then migrates up; newer archives exit 3, non-fresh databases exit 1 — D02:778-779 requires the same schema version — cost if wrong: a broken `.down.sql` blocks importing into a fresh newer site (use an empty schema or delete `ferrite.db`).
- Plan ruling P6: export never includes `secret.key`, a solo backup includes it unless `--no-secret-key`, nothing is encrypted by Ferrite, archives are `0600`, `-` is stdout/stdin for piping to `age` or `gpg` — no key management in M4 — cost if wrong: users who never pipe keep password hashes and sealed secrets in plaintext archives (the ops docs say so).
- Plan ruling P7: one archive format for export and backup: tar + zstd level 3, `manifest.json` first, export has `tables/<name>.ndjson` and optional `artifacts/<ab>/<hash>`, backup has `ferrite.db`, `ferrite.toml`, optional `secret.key` and artifacts, readers verify every sha256 — D02:773-777 and D09:111 — cost if wrong: a format change needs `format: 2` and a reader for both.
- Plan ruling P8: `db copy --from --to` streams reader to loader with no file in between, follows P5 except that an absent SQLite file is created, copies no media and writes no `ferrite.toml`; exit 0/1/3 — D02:781-782 — cost if wrong: the user edits `ferrite.toml` by hand (the command prints the lines).
- Plan ruling P9: `media sync --to [--from | --data]` copies every object under `artifacts/` (recorded or not), skips same-size keys, never deletes, never copies `tmp/`, 8 at once, URL-given S3 stores use `from_env`; exit 0/2/1 — D03:486-487 — cost if wrong: two S3 accounts needing explicit keys must share one env set.
- Plan ruling P10: the GC reference set is `media.artifact_hash`, `media_variants.hash`, `plugins.artifact_hash`, `themes.artifact_hash`, `import_runs.report_hash`, plus protected hashes from Rust (64-hex strings in queued or running job payloads, the hashes in every report manifest; all `import` rows when a manifest cannot be read) — corrects D03:473, since revisions hold content ids, not hashes — cost if wrong: a reference outside this list means a deleted blob (Task 6 covers each kind).
- Plan ruling P11: migration `0011_artifact_gc` adds `artifacts.orphaned_at` and an index (expand-only); a pass marks unreferenced unprotected rows, clears marks on referenced ones, deletes rows marked before `now - grace` with a re-checked `delete_if_orphaned` and only then the blob, deletes row-less blobs older than the grace, and cleans `tmp/` older than 24 h; `insert_if_absent` on an existing row clears the mark; grace defaults to 7 days (`[media] gc_grace_days` 1..=365) — "unreferenced for > 7 days" taken literally, protecting rollbacks — cost if wrong: one extra column and a GC that needs two runs to delete anything; accepted residual race documented in 03 §6.
- Plan ruling P12: `artifacts.gc` is a daily `Periodic` handled in `crates/ferrite/src/jobs/gc.rs` (timeout 3 600 s), `ferrite media gc [--dry-run] [--grace-days N]` runs the same `gc::run`, both take the `artifacts.gc` lock (busy: job `Busy`, CLI exit 3), and `Installer::discard_staged` stops deleting blobs — `ferrite-cluster` has no media dependency, and this closes the RM:498 same-bytes install race — cost if wrong: refused install bytes stay up to the grace period.
- Plan ruling P13: `ferrite backup --to` is SQLite only, needs `serve` stopped, writes a single `.tar.zst` or a repository (`artifacts/` shared by hash, `snapshots/<ts>/`), snapshots to `backups/backup-<ts>.db` (never `pre-*.db`), runs `integrity_check`, copies blobs, verifies the upload, `--keep N` prunes — D09:109-128, correcting BRIEF:217's "safe live" — cost if wrong: no ad-hoc live backup of a SQLite site without the schedule.
- Plan ruling P14: `ferrite restore <source> --data <dir> [--snapshot] [--force]` needs an absent or empty target (`--force` renames it to `<dir>.pre-restore-<ts>`), writes config, db, key and blobs through a `MediaStore` from the restored config, opens with `MustExist` and does not migrate; a newer schema exits 3 with nothing written — D09:114 — cost if wrong: a restore onto S3 trusts blobs already there (content-addressed).
- Plan ruling P15: `[backup]` (`schedule` off|daily|weekly, `to`, `keep` 1..=1000, `with_media`) registers the `site.backup` job (timeout 21 600 s, lock `site.backup`): SQLite runs the P13 repository backup in process, Postgres writes a P7 export and uploads it to `<to>/exports/`; failure returns `Retry` (3 attempts) — D09:113 — cost if wrong: weekly is the coarsest schedule, cron syntax is later.
- Plan ruling P16: `[media.s3]` gains `copy_if_not_exists` (object_store's own encoding) and `conditional_put = "etag" | "disabled"`, set on both builder paths; `multipart` warns in `config check` — corrects RM:446 (conditional put is already on) from the object_store 0.14.2 read — cost if wrong: a wrong header fails placements and `config check` cannot detect it.
- Plan ruling P17: `[media] strip_metadata = false` by default; when true, `stage_stream` strips EXIF and XMP losslessly from JPEG, PNG and WebP originals (ICC kept, non-1 orientation re-written as a minimal EXIF block), for uploads and the importer alike — RM:450, and the leak is the same either way — cost if wrong: deduplication against byte-identical WordPress originals stops when it is on. As built (R1): with the option on, an image whose metadata cannot be removed (over the 64 MiB strip cap, or unparseable) is refused, not stored unchanged; the plan's test `corrupt_image_is_stored_unchanged` ("stripping never fails an upload") was reversed.
- Plan ruling P18: `ferrite media regenerate [--all] [--item]` runs in process with no jobs, core sizes plus the active theme's, only items lacking a current size by default, `record_variants` conditional on the media row still holding the artifact, items over 64 MiB and non-raster skipped, replaced blobs left for the GC; exit 0/2/1 — RM:449 and P8 — cost if wrong: a solo site stops `serve` to regenerate.
- Plan ruling P19: `Store::lock_wait(name, wait)` replaces the 250 ms poll on Postgres with a dedicated connection, `SET lock_timeout`, `pg_advisory_lock` (`55P03` is `Ok(None)`, cancel drops the connection); SQLite keeps the default; lock keys unchanged — m15 R3 — cost if wrong: if `lock_timeout` did not cover advisory locks, waits would hang (Task 4's tests prove it does).
- Plan ruling P20: `seed demo` puts all blobs first, then writes every row through one `DemoBatch` over a single `Tx` (services get `*_in(tx, …)` variants where needed); a failure leaves no rows and its blobs go to the GC — RM:454 — cost if wrong: a pub(crate) seam in core grows, with seed as its only user.
- Plan ruling P21: the cluster example drops `minio/minio` and `minio/mc` for a maintained S3-compatible server and a client with a shell, all images pinned by digest and verified with `docker compose up` (upload on node1 read through node2) — RM:486 — cost if wrong: the image moves on and the digest goes stale.
- Plan ruling P22: docs/design/09-operations.md gains §4a "S3 media buckets" (lifecycle rules, `copy_if_not_exists` per provider, R2, B2, Hetzner, Scaleway), each provider claim checked against current documentation and listed in a verified / not verified table — user rule on checking claims — cost if wrong: an unverifiable claim stays in the "not verified" table and is not stated as fact.
- Plan ruling P23: the new commands and jobs are operator CLI with no `audit_log` rows, API or admin surface (as for `user` and `ext`) — a Backups screen and API are later items (m2b P25) — cost if wrong: operator actions are not audited.
- Plan ruling P24: `docs/superpowers/m4-1-exit.md` lists each command run end to end on both profiles, the SQLite to Postgres move, a backup taken while `serve` runs and restored into a new folder, the cluster example brought up, and a "Not verified" table — cost if wrong: unverified claims slip into the exit.

## M4-1 execution rulings

Numbered as in the execution ledger. R-pf1–R-pf3 are the pre-flight controller rulings, R1–R14
come from the task reviews, R15–R19 from the final review and its fix rounds, R20 from the exit. "Amends" names the
plan ruling whose text the code no longer follows exactly; "adds to" one it leaves open.

- Ruling R-pf1 (amends P4): the reader requires the source at the binary's latest schema, and the loader writes the columns present in each archive row (each must be a catalogue column) — migrations are expand-only, so an older archive loads into a database at its own version — cost if wrong: a future column drop needs a versioned catalogue.
- Ruling R-pf2: whichever of Tasks 6 and 7 landed first created `media_cmd.rs`, the other added its subcommand, and the controller resolved the merges — one-line enum conflicts — cost if wrong: merge work only.
- Ruling R-pf3: the independent lanes (A: Tasks 1→2→3, B: 4, C: 10→7, D: 12→13) ran as parallel worktree subagents, each task reviewed on its own — independent files — cost if wrong: merge work in `cli.rs`, `lib.rs` and the config crate.
- Ruling R1 (amends P17): with `media.strip_metadata` on, a JPEG, PNG or WebP whose metadata cannot be removed (over the 64 MiB strip cap, or unparseable) is refused (an upload gets the error class of other refused media, `422`; the importer records refused media in its report), never stored with its metadata; the image stays buffered whole (no streaming walker in M4-1) and 01 §4 states the strip-on memory peak — the operator opted in to "no location leaks", which a silent keep would break — cost if wrong: a rare huge or slightly corrupt photo must be fixed, or uploaded with the option off.
- Ruling R2: `MediaStore::list_artifacts` is built in Task 7 (sync needs it first) and Task 6's GC reuses it — ordering of the lanes — cost if wrong: none.
- Ruling R3: the `0011_artifact_gc` down is not lossy (Task 1's first draft marked it lossy), like `0003` — the marks only delay deletion and the next pass marks again — cost if wrong: none.
- Ruling R4: `ferrite-config` keeps its dependency on `ferrite-media` (for `ConditionalPut` and the `copy_if_not_exists` check) — no cycle, no binary cost, and the value's validation stays object_store's own — cost if wrong: slower builds of the config crate.
- Ruling R5 (adds to P9): a copy from a corrupt source leaves its bytes at the destination under their own valid hash, an orphan for that site's GC — never under a wrong key (`copy_to` checks hash and size) — cost if wrong: unreferenced bytes until a GC pass.
- Ruling R6 (amends P4): self-referencing rows are held until their parent is loaded, then inserted with the real parent, not NULL-then-update — the update breaks `content_items_slug_uq` (`NULLS NOT DISTINCT`) — cost if wrong: memory for the waiting rows and the loaded keys of the self-referencing tables.
- Ruling R7 (amends P4): any failed loader call poisons the loader, validation refusals included (stricter than m1a R18's `Tx` rule) — keeps a load all-or-nothing, and avoids Postgres turning a `COMMIT` of an aborted transaction into a silent rollback — cost if wrong: none for a fresh target.
- Ruling R8 (amends P4): a self-referencing row whose parent is not in the same load is refused — targets are fresh (P5) and migrations seed no self-referencing rows — cost if wrong: a partial archive cannot load.
- Ruling R9 (amends P6's `-` list): `db copy` takes URLs only, no stdin — P8 wins; archives are the only `-` sources — cost if wrong: none.
- Ruling R10 (amends P7, P13): `export --with-media` (and every backup) with a blob missing from the store completes with exit 2, one stderr line per hash, the count in the summary and an additive `missing` list in the manifest (format stays 1); a blob whose content does not match its hash fails it (exit 1) — a missing file is reportable loss, a corrupt one must not be archived — cost if wrong: a wrapper that treats exit 2 as written must also check the file (clap usage errors are 2 too).
- Ruling R11 (amends P13): a backup repository is marked by `<repo>/ferrite-backup-repo.json`, written on first use; a non-empty folder or prefix without it is refused (exit 1), so is one inside the data folder or the media root; prune deletes repository `tmp/` objects only when older than 24 h — `--keep` must never delete files Ferrite did not write — cost if wrong: one extra object per repository.
- Ruling R12 (amends P13): a snapshot's artifact list goes to `snapshots/<ts>/artifacts.txt` (one hash per line), its sha256 and count in `manifest.json`; readers stream it with a per-line cap — no manifest size ceiling for big sites — cost if wrong: one more file per snapshot.
- Ruling R13 (amends P14): restore into an existing empty folder (a mount point too) stages inside it and moves the entries into place; `--force` on a folder that cannot be renamed (mount point, `EBUSY`, cross-device) is refused before any work, with a message to restore into an empty folder instead (documented for Docker `/data`) — a mount point cannot be renamed — cost if wrong: a bind mount on the same device is only detected at the final rename (it then changes nothing).
- Ruling R14 (amends P13, P15): repository prune deletes unreferenced blobs only when older than 24 h; restore warns when the restored config has a `[backup] schedule` other than `off`; `serve` refuses to start on a bad `backup.to` — a snapshot still being written into a shared repository lists its blobs only in its last-written manifest — cost if wrong: unlisted blobs stay a day longer; on S3 a reused old blob is not re-aged (no mtime update), see the ROADMAP follow-up.
- Ruling R15 (superseded by R16): a media store shared by two sites was to be unsupported and only warned about.
- Ruling R16 (amends P11, P12, P14, P5, P8): each database has an install id (`schema_meta.install_id`, a UUID, never exported: `schema_meta` exports only `site_id`), written by the migrate step when absent (the GC calls it too); `restore` gives the restored site a new one, `import-site` and `db copy` targets keep the fresh one their migrations wrote. The media store holds `<prefix>ferrite-owner.json` `{install_id, site_id, claimed_at}`. The GC's deleting steps (2 and 3) run only when the marker names this install; otherwise they are skipped with an error log and the report says so (step 1 and the `tmp/` sweep still run). `ferrite media gc --claim` rewrites the marker for a site that really replaced the owner (restore in place); `restore` and `import-site` warn when the media store is outside DIR — a restored or staging copy on the same store would otherwise delete the live site's blobs (final review, Critical) — cost if wrong: one marker object and one extra command for in-place recovery.
- Ruling R17 (amends P12, P13, P15): the scheduled and the CLI backup hold `artifacts.gc` (via `lock_wait`, up to 300 s; still held: the job is `Busy`, the CLI exits 1) from before the snapshot until the blobs are written, and so does the scheduled Postgres export — the GC must never delete a blob a backup is copying — cost if wrong: a worker waits up to 5 minutes; the 00:00 UTC contention is a follow-up.
- Ruling R18 (amends P16): the `header:x-amz-copy-source-if-none-match:*` example is removed everywhere; after an `AlreadyExists`/412 on placement the final key is read back (`head`) and the upload fails if it is absent — that header is a precondition on the copy source, so a provider answering 412 would make every large upload vanish silently — cost if wrong: one HEAD per placement that reports an existing object.
- Ruling R19 (amends R16): the GC pass that writes (or finds no) owner marker deletes nothing; deletes start on a later pass that reads its own install id; backup snapshots drop the `install_id` row (restore and a hand-unpacked archive get a fresh one); 09 §4 documents the install-id reset for PITR, `pg_dump` and `cp` clones — on a store that does not honour the conditional create, two installs that both find no marker would both delete in that pass — cost if wrong: a new store waits one pass before deleting. Accepted residuals: the GC/backup 00:00 UTC contention (follow-up), the CLI `export --with-media` on Postgres without the GC lock (R10 reports a raced blob), and the one-pass wait.
- Ruling R20: the stale `running` `site.backup` row inside a scheduled snapshot (the job's own row, copied with the database) is accepted for M4-1 — `restore` already warns about the restored schedule, and a restored site with the schedule on takes one extra snapshot after the lease expires — cost if wrong: one extra snapshot; follow-up in the ROADMAP ("Deferred from M4-1").

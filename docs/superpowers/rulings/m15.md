# M1.5 cluster mode — plan and controller rulings

Decisions made while planning and executing docs/superpowers/plans/2026-10-23-m15-cluster.md (subagent-driven). Format: ruling — reason — cost if wrong.

- Plan ruling P1: coordination follows the database backend, not the mode (Postgres: `SKIP LOCKED`, advisory locks, `LISTEN/NOTIFY`; SQLite: single-writer claim, in-process mutex, no subscription); `cluster.mode` only decides listening, the solo single-live-node rule and whether `data/themes/` is read — a solo node on Postgres still shares its database with `ferrite migrate` or a second node — cost: solo-on-Postgres sends NOTIFYs nobody listens to.
- Plan ruling P2: `pg_notify` runs inside the writing `INSERT … RETURNING` of `events.append` / `jobs.enqueue`; channels `ferrite_events[_<schema>]` / `ferrite_jobs[_<schema>]`, lowercased; payload seq / kind, hints only; `database.schema` capped at 48 bytes — delivered only at commit and no write path can forget it — cost: schemas differing only in case share a channel (extra polls).
- Plan ruling P3: wake-ups are hints; a `Reconnected` notice or the first good poll after failures runs a history check via `EventRepo::min_seq`, and lost history flushes the cache, reloads node state and moves the cursor — notifications between connections are lost — cost: one `min_seq` query per reconnect.
- Plan ruling P4: `idle_in_transaction_session_timeout = 60s` on Postgres app connections — well under the 10-minute late horizon — cost: a `Tx` idle for 60 s is killed; long busy statements are not bounded.
- Plan ruling P5: claim filters `kind = ANY($kinds)`; an unknown payload `v` is released after the backoff with the attempt refunded; no `v` = version 1; the claim is a `MATERIALIZED` CTE — an old node must never burn attempts on new work — cost: a kind no running node knows waits forever (visible as queued).
- Plan ruling P6: lease token = (job id, node id, attempts) on every lease-holder write — a lapsed holder, even one that reclaimed its own job, cannot overwrite the current attempt — cost: none.
- Plan ruling P7: an expired lease at `max_attempts` goes `dead` (reaper statement in `claim`) — 04's claim SQL never stopped reclaiming a job that kills its node — cost: one extra UPDATE per claim call.
- Plan ruling P8: no `failed` status; CHECK allows `queued`, `running`, `done`, `dead` — 04's semantics never produce `failed` — cost: adding a status later needs a SQLite table rebuild.
- Plan ruling P9: the runner renews every lease every 20 s; handlers have `timeout()` (default 300 s); `JobError::Permanent` goes straight to `dead` — handlers need no lease code and a hung handler cannot hold its lease forever — cost: the M3 import must override `timeout()`.
- Plan ruling P10: shutdown stops claiming, gives in-flight jobs 9 s, then releases the rest with the attempt refunded — another node takes them at once instead of after the 60 s lease — cost: a job that cannot finish in 9 s restarts elsewhere.
- Plan ruling P11: periodic jobs use the database clock: `<kind>:<floor(db_now / period) × period>` with `ON CONFLICT DO NOTHING`, ticked every 10 s per node — one row per period cluster-wide without a leader — cost: periodic rows accumulate until `jobs.prune`.
- Plan ruling P12: `schedule` enqueues `content.publish_scheduled` with `unique_key = "publish:<id>:<scheduled_at micros>"`, `run_at = scheduled_at`; the 30 s ticker became the periodic `content.publish_due` safety net — `publish:<id>` would block rescheduling — cost: one extra row per (re)schedule.
- Plan ruling P13: session-level `PgAdvisoryLock("ferrite:<schema>:<name>")` on a dedicated connection per held lock, `try_lock` polled every 250 ms; names `migrate` (5 min), `extensions` (30 s), `import` (reserved); SQLite in-process mutex — released for certain when the connection dies — cost: one connection per held lock.
- Plan ruling P14: heartbeat 10 s, stale after 30 s, rows pruned 24 h after the last heartbeat, deregistered on clean shutdown; name `cluster.node_name`, else `$HOSTNAME-<pid>`, else `node-<pid>`; skew measured at the round-trip midpoint, warned above 2 s; `nodes.meta` keys fixed — values from 02 §4 and 04 §3 — cost: none.
- Plan ruling P15: a live node with another `site_id` or another `site.url` refuses start; solo waits up to 35 s for another live node, then refuses — a wrong schema/search_path is caught by `site.url`, not by `site_id` — cost: changing `site.url` needs all old nodes stopped.
- Plan ruling P16: `cluster.workers` default `max(2, available_parallelism)`, explicit 1..=256 — 04's "CPU count, min 2" — cost: none.
- Plan ruling P17: theme bundles are plain deterministic ustar (`application/x-tar`), unpacked in memory with the folder limits, not `tar.zst`; cluster mode ignores `data/themes/` — zstd needs a C library and themes are ≤ 20 MiB — cost: larger artifacts.
- Plan ruling P18: hot swap runs on one background task (coalesced, re-read from the database), flushes after each swap, and keeps the old version on failure (reported in `nodes.meta`, no runtime fallback to `blog`) — a bad change must not take nodes down — cost: two flushes per change.
- Plan ruling P19: no on-disk artifact or precompiled-component cache; reuse is in memory by hash — `Component::deserialize` is `unsafe` and a byte cache saves little — cost: slower restarts with many plugins (M4 revisit).
- Plan ruling P20: shared failure counters: per-node buffer flushed every 5 s into 1-minute buckets (database clock), threshold summed over `plugins.failure_window`, `auto_disable` conditional so exactly one node emits `plugin.disabled`; enabling clears the counters; retention `max(24 h, 2 × window)` — cluster-wide disable without a coordinator — cost: disable lags up to ~5 s.
- Plan ruling P21: install/activation writes live in core (`ExtensionService`: artifact row + theme/plugin row + event in one `Tx` under the `extensions` lock), no CLI; the binary's `install_theme_dir` / `install_plugin_file` upload first — keeps M1.5 small — cost: operators cannot install from the CLI until M2.
- Plan ruling P22: `serve` creates the invalidation cursor before reading permalinks, theme and plugins — a change committed during boot must be applied by the first poll — cost: a boot-time change may be applied twice (idempotent).
- Plan ruling P23: M1c-2 R14 (template memory) stays deferred, to M4 (render worker) — a counting allocator cannot fail one allocation gracefully and MiniJinja has no check point but fuel; M1.5 adds no untrusted install path — cost: an operator-installed hostile theme can OOM every node at once.
- Plan ruling P24: the compose example is verified locally by `cluster_example_config_is_valid` (config + env + `ferrite config check`) and in CI by `docker compose config` and `docker build`; `docker compose up` is not run — Docker is unusable on the development machine — cost: runtime wiring problems (Caddy health checks, MinIO bucket init) surface only when someone runs it.
- Plan ruling P25: "killing a node mid-job" is verified in process (`RunningNode::abort()` + `pg_terminate_backend` of its connections) — no production job runs long enough to SIGKILL a child reliably — cost: OS-level kill behaviour is not exercised.
- Plan ruling P26: not in M1.5: `node.drain` handling, `plugin.action` jobs (M2), `artifacts.gc` (M4), `sessions.prune` (M2), `revisions.prune` (core prunes on save), `/metrics` and `node_metrics` (M4), PgBouncer transaction pooling — scope — cost: listed in the roadmap.
- Plan ruling P27: new migration `0004_cluster` (expand, `lossy-down`), not edits to `0001` — exercises the upgrade path and the lint — cost: none.
- Plan ruling P28: events are versioned by kind, not payload (no payload column); job payloads carry `v`; an unknown event kind invalidates its keys — 04 §9's `{"v":1}` fits job payloads only — cost: none.
- Ruling R1: Postgres `jobs_claim_idx` is `(priority DESC, run_at, id) WHERE status IN ('queued','running')` (0004 edited while unreleased) — the old index did not serve the claim's ORDER BY (44 ms vs 0.5 ms at 100k rows) — cost: none.
- Ruling R2: accept Postgres NOTIFY commit serialisation (global notify-queue lock at commit) — CMS write rates are low — cost: a write throughput ceiling under bulk import (M3: batch events per `Tx`).
- Ruling R3: keep P13's connection-per-poll while waiting for a lock; a single held connection with `lock_timeout` is M4 — simplicity — cost: connect churn during contended waits.
- Ruling R4: local lease fencing: a job is cancelled when no renewal succeeded for `lease − extend_every / 2`, whatever the store reports, and every runner store call is bounded at `extend_every / 2` — a partitioned node must drop its handler before its lease ends — cost: a slow database can abort healthy jobs (they rerun; idempotent).
- Ruling R5: prune store APIs take a limit (≤ 10 000); handlers delete in batches within 240 s — the first prune of an upgraded backlog must not exceed `statement_timeout` — cost: trait change.
- Ruling R6: `serve` waits at most 12 s for the job runner at shutdown, then abandons it — hard 14 s process bound — cost: a stuck claim may leave a job leased until expiry.
- Ruling R7: `Registry::join`'s final check-and-register pass holds the `cluster.join` lock (10 s wait), never across the solo sleep, in both modes — check-then-register raced for simultaneous starts — cost: one short lock connection per start.
- Ruling R8: solo nodes re-check for other live nodes on every heartbeat and log an error on the transition (no self-fence) — detection only; leases keep correctness — cost: one list per beat.
- Ruling R9: `events.prune` never deletes the newest event row — so `min_seq > 0` whenever history existed and lost history is always detectable — cost: one row kept forever.
- Ruling R10: `Permalinks::pin()` snapshots the rules once per `ContentService` write and per `SiteReader` call — mixed old/new rules within one write could record a persistent bogus redirect — cost: one clone per operation.
- Ruling R11: `ExtensionService` is an unauthenticated system path; the M2 admin API must check `ManageThemes` / `ManagePlugins` first — no auth exists yet — cost: none now (M2 obligation).
- Ruling R12: `auto_disable` is optimistic on the row's `updated_at` observed before summing; buffered counts older than the reloaded row are dropped — an admin re-enable must not be reverted by stale sums — cost: a racing failure burst may need one more window to disable.
- Ruling R13: a page render may mix plugin versions across a hot swap (per-call registry snapshot); safe because the post-commit flush refuses straddling inserts, so the node flushes after each committed reload — cost: transient mixed output, never cached; M2 `plugin.action` jobs must snapshot the registry per call.
- Ruling R14: a failed hot reload retries per component after 5 s, doubling to 5 min, until success or a newer event — a transient S3 blip must not leave a node on an old version forever — cost: periodic retries while broken.

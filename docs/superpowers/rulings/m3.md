# M3 WordPress import — plan and controller rulings

Decisions made while planning and executing the M3 sub-plans (subagent-driven). M3-1:
docs/superpowers/plans/2026-10-28-m3-1-wordpress-import-core.md (18 tasks). M3-2:
docs/superpowers/plans/2026-10-29-m3-2-import-job-api-admin.md. Format: ruling —
reason — cost if wrong. P = plan rulings (full text in the plan), R = controller rulings during
execution. Where the code differs from a ruling's text, the line says "as built".

## M3-1 plan rulings

- P1: the import writes through a new core API (`ferrite-core::import`, `ImportService`/`ImportBatch`), checked once with `Capability::Import` — the public services commit per call and cannot set dates, author, private, meta or comment status — cost: a second write path whose invariants must match the services'.
- P2: M3 is two sub-plans; M3-2 holds the job and API, admin screen, permalink-change redirects (M2a-2b P26), the job-claim EXPLAIN (m15 R17) and the M3 exit — cost: CLI-only import until M3-2.
- P3: idempotency in a persistent `import_map(source, kind, wp_id → ferrite_id, hash, version)`; `import.wp.id` meta is written, never read — the temp IR alone cannot dedupe a re-run from a fresh upload — cost: rows outliving deleted items (treated as unmapped). As built: the hash covers what is written (the converted item, the resolved menu, the option value), not the WXR record (final review C2).
- P4: re-run: same hash skip; changed hash and unedited update; edited locally keep and report; gone recreate — cost: local edits block later WP fixes for that item.
- P5: fence = run token checked by an `UPDATE import_runs … WHERE token AND running` first in every batch tx; 120 s stale heartbeat; takeover only on request; `LOCK_IMPORT` best-effort — the advisory lock is not a fence (m15 R17) — cost: one UPDATE per batch.
- P6: batches of ≤500 items, one invalidate event per batch (`[all]` past 1 000 keys), revisions and search written, no plugin actions — R2 (NOTIFY serialises commits) — cost: plugins never see imported items as saved.
- P7: status and date mapping (future in the past → published and reported; GMT dates, local as UTC when GMT is zero) — cost: offset shift on sites without GMT dates.
- P8: WP slugs kept exactly where core allows, else `-N` and reported.
- P9: users matched by e-mail, then login, else created without password, `must_reset`, role author (WXR has no roles, verified) — cost: everyone is an author until changed.
- P10: SEO gains `seo.canonical` and `seo.robots`; Yoast and Rank Math keys verified in plugin source and real exports 2026-10-28; title variables substituted (`sep` = `-`) — cost: per-type title templates are not in WXR.
- P11: block tree gains an `embed` node (YouTube, Vimeo; privacy-mode iframes) and an image `caption`; layout blocks flattened; unsupported marks dropped and counted — cost: lost layout.
- P12: unknown blocks → `html` node (dropped when empty), unknown shortcodes stay text; both counted with examples — cost: preview-only html blocks in the editor.
- P13: media from `--uploads`, or `--fetch-media` through the SSRF-checked client; same sniffing as uploads; variants by the next `serve` — cost: no srcset until a server ran.
- P14: every attachment URL form (sizes, `-scaled`) rewritten; img → `ferrite:media/<uuid>`, links → public URL; internal links fixed after all content exists.
- P15: synthetic corpus A/B checked in; WordPress theme-test data (GPL-2.0) via `FERRITE_WP_CORPUS` only — cost: CI skips the big files. As built: the two upload folders hold 128 408 bytes (188 KiB on disk), not the plan's 1.4 MB.
- P16: ACF definitions read from the export's `acf-field` items and mapped per the plan's table; others raw `wp.<name>` meta; ACF on built-ins stays meta — cost: manual modelling for built-ins.
- P17: permalinks: WXR has no options (verified); old URL = `<link>`; infer a post structure when all posts fit, then redirect every differing path, attachment pages and tag/category bases — cost: unsupported WP tokens (`%day%`, `%post_id%`) end up as redirects.
- P18: comments to plain text, status mapping, pingbacks skipped, threading kept, `by_account` for mapped users — cost: lost comment formatting.
- P19: menus from `nav_menu_item`, one per `nav_menu` term; no locations (not in WXR).
- P20: channel title and description → `site.title`/`site.description` unless `--no-site-options`.
- P21: IR = temp SQLite under `<data>/import/<run-id>/`, passes recorded, deleted on done. As built: keyed by the WXR's SHA-256 so a failed run is resumed by the next run of the same file (R27); a dry run's IR is deleted on every exit (R49).
- P22: XML safety: no DOCTYPE, 64 MiB text cap, UTF-8 checked, streaming.

## M3-1 execution rulings

Numbered in the order they were made. R1–R4 are the pre-flight controller rulings; the
rest come from the execution log, then the accepted final-review items.

- R1: `ImportOptions::batch_items: Option<usize>` (behind `test-seams`) lets Task 15 force 3 items per batch — the T15 test needs it and T9 owns `ImportOptions` — cost: one more seam field. As built: the default is `ImportBatch::BATCH_ITEMS` (500).
- R2: Task 13's harness creates the importing admin with e-mail `a@example.test`, so WXR `admin` is asserted as `Matched::Email` — removes an "if" from the test — cost: none.
- R3: ACF `quotes` in site A (free ACF, a repeater without exported sub-fields) is reported unmapped and kept as `wp.quotes` raw meta — it is what the corpus holds — cost: none.
- R4 (corrected): "Every core block" has 3 comments in the WXR (2 approved and threaded, 1 pending) — WordPress's exporter omits spam comments, and the corpus is the truth — cost: none. The first text (4 comments with 1 spam) was wrong.
- R5: `import_runs.started_by` is `ON DELETE CASCADE`, not `RESTRICT` — `RESTRICT` would block deleting any user who ever ran an import, and the audit log's `SET NULL` needs a nullable column — cost: deleting that user drops their run history (`import_map` is unaffected).
- R6: `ImportService` gets fields only when a task uses them — no dead fields (user rule) — cost: the constructor changed across tasks. As built: `ImportService::new(store, permalinks)`.
- R7: a taken-over run is `CoreError::Changed` (409) and a busy one `Unavailable` (503) — `Conflict(&str)` does not exist — cost: none.
- R8: content types, taxonomies and `permalink.*` options are written only through schema batches (`ImportHandle::schema_batch`, which takes the types lock before the transaction) — keeps the lock order — cost: two batch kinds.
- R9: a term whose (taxonomy, slug) is already on the site is reused and mapped, not created as `-2` — both systems have defaults such as `uncategorized`, and merging is what a re-import into a seeded site expects — cost: a same-slug local term of another meaning absorbs imported items (reported as matched).
- R10: WP percent-encoded slugs are decoded before terms and content are written; an invalid or missing WXR e-mail gets a placeholder and is reported — cost: placeholder e-mails to fix by hand. As built: the placeholder is `wp<id>.<login>@users.invalid` (R26).
- R11: a reused site term keeps its own parent when WP has it under another — the site's tree is the admin's — cost: the imported hierarchy differs for that term (reported).
- R12: `ContentRepo::set_updated_at` (contract-tested on both backends) is an extra store method — it keeps WP's modified date across re-runs and the fix-up — cost: one more store method.
- R13: the redirect helpers return the sources they touched so a batch sends one event — same keys, fewer NOTIFYs — cost: none. As built: `ContentService::update` also sends a single event since final review A5.
- R14: the link fix-up writes no revision (the import's revision holds the pre-fix-up body) — accepted for M3-1 — cost: restoring the import revision brings back old-site links. As built: `ImportBatch::set_body` was removed (final review A3); the fix-up is `set_body_and_fields`, which also writes no revision.
- R15: a comment already mapped is not updated on a re-run (no hash compare) — comments carry no version to detect local moderation — cost: WP-side moderation after the first import is not mirrored.
- R16: `ImportBatch::menu` is a plain put; the menus pass records the map row itself (`remember`) — keeps `menu()` simple — cost: none.
- R17: both rows of a redirect 2-cycle are refused; the published-path check walks slugs per row — acceptable for import sizes (≤10 000 per chunk) — cost: slower big redirect sets.
- R18: imported comment bodies have control characters removed and are truncated past the length cap, counted — one bad comment must not fail a 500-item batch — cost: altered text (reported). Extended by final review A1 to the author's name, e-mail and URL.
- R19: an unknown `seo.robots` value is 400 (malformed JSON, a serde type error), not the brief's 422 — it is how the API reports every DTO type error — cost: one status code differs from the plan text.
- R20: Tasks 7 and 8 ran as separate worktree sessions from `m3-import`, reviewed and merged by the controller; Tasks 10 and 11 followed after Task 8 merged — the user asked to parallelise — cost: merge work and separate target folders.
- R21: `canonical_embed_url` returns `Option` (`None` for an unknown provider); the sanitiser keeps a valid frame and drops its extra attributes — safer than all-or-nothing, same visible result — cost: none.
- R22: WXR prefixes are matched literally (`wp:`, `content:`, `excerpt:`, `dc:`), not by namespace URI — every WordPress export writes them — cost: an exotic re-prefixed WXR parses as empty.
- R23: `Record::Item(Box<Item>)` (clippy's large-variant lint) is accepted — cost: none. P15's "1.4 MB" of uploads was a ruling text error (see P15).
- R24: the DOM is `scraper 0.29` (default features off) on `html5ever =0.40.1` — `markup5ever_rcdom` has no release for html5ever 0.40, and the lockfile keeps one html5ever — cost: scraper's selector dependencies compiled for one crate.
- R25: Gutenberg attributes with a literal `-->` inside a JSON string stay text — WordPress's serialiser escapes `--` — cost: a hand-written comment with it loses its block.
- R26: placeholder e-mail = `wp<id>.<login>@users.invalid` — distinct WP authors must stay distinct — cost: an uglier placeholder.
- R27: resume keys the IR by the WXR's SHA-256 (not the run id) and renames the folder to the new run's — the IR holds no site data, so reuse across runs is safe — cost: folders of other files linger until pruned.
- R28: WP attachment parents are not imported in M3-1 (pass 2 runs before content, and nothing reads media parents); the dead lookup was removed — cost: the "uploaded to" link is lost.
- R29: a dry run stages media into a throwaway store under the run's work folder — a dry run writes nothing (T9/T17 contract) — cost: one extra temporary copy.
- R30: Task 12 review: no shortcode expansion inside `<pre>`; expansion in paragraph and list blocks; a bare URL line becomes a link unless it is YouTube or Vimeo (WP's linkify of unknown URLs); `<!--more-->` dropped uncounted; `<!--nextpage-->` counted (not dropped silently) — WordPress behaviour — cost: none.
- R31: a depth guard of 512 levels runs before every html5ever parse, html-node payloads included; a tripped body becomes plain-text paragraphs, counted as `too deep` — html5ever is quadratic on deep nesting and the WXR is untrusted — cost: a legitimately deeper body loses its formatting. As built: `convert::depth::MAX_PARSE_DEPTH` = 512.
- R32: the guard drives html5ever's own tokenizer with a stack sink (superseded by R33) — hand-rolled lexing cannot match html5ever — cost: a second linear tokenize per body.
- R33 (supersedes R32): the guard is html5ever's real tree builder over a counting `TreeSink` (arena, depth = parent + 1), fed in ~4 KiB chunks, aborting past 512 — emulating the tree builder kept leaking; the real builder is exact and chunking bounds the work before an abort — cost: one extra, bounded parse per body.
- R34: the guard also counts marker-pushing elements (`object`, `applet`, `marquee`) and trips at 1 024 per body — cost: a page with more than 1 024 of them becomes text; counting `template` as a level over-counts (accepted). As built: `MAX_MARKER_ELEMENTS` = 1024; `td`, `th`, `caption` and `template` clear their markers when they close (measured linear), so they are not counted.
- R35: a repeated meta key becomes a JSON array of strings — no data loss — cost: consumers must handle string or array.
- R36: links to drafts and trashed items resolve to their new (non-public) paths — matches WordPress's 404 for them — cost: none.
- R37: options, `permalink.post`, menus and redirects follow P4 through the import map's hash of the last imported value; a local change is kept and noted; `permalink.post` is set on the first import only while the site has core's default — local configuration wins — cost: the WP structure is ignored on customised sites.
- R38: data problems in comments and menus are noted and never fail a batch.
- R39: a native menu of the same name is kept; the import's goes under `<name>-wp` (then `-wp-2`, …).
- R40: the unreleased `0009_import` migration was edited in place to add kind `option` (both backends) — 0009 exists only on `m3-import`, never on `develop` or `main` — cost: a local dev database that applied the old 0009 must be recreated. As built: the kind check lists `user, term, media, content, comment, menu, option, redirect`.
- R41: the import owns a stored redirect only if `import_map` records it or the row equals the last write; anything else is kept and noted — cost: one map read per redirect source.
- R42: report lists are capped in the model at 1 000 with totals; notes are collapsed per kind (500 kinds, then a total); `dropped_formatting` keeps the top 100 plus `other`; HTML tables show 200 rows, then "N more" — cost: the JSON is no longer exhaustive for huge failures.
- R43: a resumed run's report starts with a note listing the steps run now.
- R44: no host allowlist for `--fetch-media` (CDNs are common); the SSRF address rule protects internal hosts.
- R45: a remote I/O error during a body read means missing media; an `https` → `http` redirect is refused; exit 2 also covers media refused for size or type.
- R46 (final review C6, accepted): terms are matched or reused and not updated on a re-run — local taxonomy edits win — cost: a term renamed in WordPress keeps its old name here.
- R47 (final review A2, accepted): an item the import scheduled and that has since been published by its schedule counts as kept (edited here) on a re-run — publishing bumps the version and lifecycle transitions write no revision, so telling it from an edit needs the imported status in the map — cost: such items are not updated from WordPress; the report notes it whenever items were kept, and design 08 §6 says so.
- R48 (final review B2): converted bodies are capped at 48 node levels (`convert::doc::MAX_DEPTH`); a blockquote, list item or cell at that depth keeps its text in one paragraph, counted as `too deep` — `serde_json` refuses JSON nested past 128 levels, so a deeper body could not be read back — cost: images, embeds and HTML below the cap are dropped.
- R49 (final review residual): a dry run's IR stores a `dry-run` marker instead of the WXR digest and is deleted on every exit; of several resumable folders `find_ir` takes the one with the most finished passes — a failed dry run must never stand in for a failed real run's fix-up queue — cost: a dry run never speeds up the next real run.
- R50 (final review residual, accepted): a resumed pass 3 can produce one spurious `updated` on the next re-run — it heals itself — cost: one extra write.
- R51 (final review A4): `ImportHandle`'s `run` and `actor` are private; `run()` reads the run, and there is no `actor()` getter because nothing outside `ferrite_core::import` reads it.

## M3-2 plan rulings

- P23: the API's inputs (the WXR, the optional uploads zip) are streamed into the `MediaStore` as artifacts of a new kind `import` (`0010` widens `artifacts.kind` on both backends); the job copies them to `<data>/import/job-<job-id>/` on the node that claims it; caps `IMPORT_MAX_WXR` 512 MiB and `IMPORT_MAX_ARCHIVE` 4 GiB, route limit their sum plus 1 MiB; the artifacts are deleted when the run is `done` or the job `dead` — in cluster mode the receiving node is not the running one — cost: the upload briefly exists twice. As built (Task 1): Postgres swaps the CHECK in one `ALTER TABLE` (expand; the expand lint accepts a same-name `CHECK (col IN (…))` swap only when its list is a strict superset of the one the down restores); SQLite rebuilds `artifacts` with deferred foreign keys, so its `0010` is a contract migration (no min-binary: the CHECK only widens).
- P24: an uploads archive is a zip read in place (`ZipSource: MediaSource`, central directory, matched below the first `uploads/` segment or by full path; absolute or `..` names refused; `max_upload` plus declared-vs-actual size per entry; over 500 000 entries or 64 GiB declared refused; stored and deflate only) — WordPress uploads ship as zips and need no extraction space — cost: one new dependency (`zip`). As built (Task 3): the end records (zip64 too) are read before the central directory is parsed, refusing over 500 000 declared entries or a directory over 64 MiB (R58); entry names compare in NFC; `zip =9.1.3` with `deflate-flate2-zlib-rs` (R59).
- P25: `POST /import/wordpress` is multipart (`wxr`; optional `uploads`; optional `options` JSON ≤ 4 KiB with the CLI's defaults), idempotent with `Idempotency-Key` under the media upload's rules, `202` with `ImportJobDto` and `Location`; `413` over a cap, `400` malformed, `409` while an import job is queued or running or a run is `running`; `takeover` is not exposed (P27) — cost: none. As built (Tasks 2, 5): the refusal is `CoreError::Changed` (`409 conflict`), first from a read-only pre-check before the body is read, then authoritatively in the enqueue transaction (R67); a stale running run is abandoned by the enqueue instead (R65).
- P26-1: read API `GET /import/jobs/{job_id}`, `GET /import/runs?limit&cursor`, `GET /import/runs/{id}` and its `report.json`/`report.html` (HTML under `default-src 'none'; style-src 'unsafe-inline'; sandbox`, `nosniff`, `private, no-store`); `import:read` to read, `import:write` to start; design 07's `GET /import/{job}` is as built as these routes — cost: a wider API than the doc's single row. As built (Task 5): these routes, under `/api/v1`.
- P27: job kind `import.wordpress`, payload `v` 1 `{wxr, uploads?, options, user, source_name}`, no `unique_key` (P25's conflict rule), `max_attempts` 3, `timeout()` 6 h; a user no longer an active admin or a missing artifact is `Permanent`; `Unavailable` → `Busy`, `Changed` and input/parse errors → `Permanent`, the rest → `Retry`; a retry takes over only its own stale run (same `job_id`); the working folder is node-local and a retry elsewhere re-parses — at-least-once execution with resume on the same node — cost: a retry on another node redoes the parse. As built (Task 4): a job's start takes over a stale run that has no job, is its own, or whose job is not `running`, in one statement (R69); a busy attempt fetches nothing; a `Retry` of the last attempt also deletes the inputs (R70); the handler is built in `serve`, not `jobs::handlers()`.
- P28: `0010` adds `import_runs.job_id`, `step` (`parse`, `pass1`…`pass4`, `fixup`, `report`) and `report_hash`; `ImportHandle::set_step` writes `step` under the run-token fence as each step begins (production code, not a seam); the admin shows "step N of 7" and `heartbeat_at` — cost: no per-item percentage. As built (Tasks 1, 4): `ImportRepo::create_run(&ImportRun)` (no `NewImportRun`), `step` free text in the store and checked in core (R57); the driver writes the step between steps, never with a batch open.
- P29: a failed run still gets a report: `run::run` returns `RunFailed { error, report: Option<Report> }`, built from the surviving IR with `failed: {step, error}` and a leading note; the CLI writes it and exits 1, the job stores the report artifact on every attempt — cost: a partial report counts only the last attempt. As built (Tasks 2–4): `RunFailed.report` is `Option<Box<Report>>` (R60); `report_hash` names a manifest artifact `{"v":1,"json","html"}` over the two report files; a failed report store is logged, not retried.
- P30: every write of `permalink.post`/`permalink.page` (options service and `ImportBatch::options`) enqueues `permalink.redirects` in the same transaction with the previous and new values; the job walks published items 500 at a time and writes `old → new` with origin `slug-change` through `move_redirects`, refusing live paths and keeping `manual`/`import` rows; `unique_key` `permalink.redirects:<options-version>`; term-path changes stay out of scope (noted in 06); the Settings confirm copy says redirects are created — cost: old URLs 404 until the job finishes; one row per moved item. As built (Task 6): pages by a published-order cursor, not by id (R62); each page re-reads the stored rules under `LOCK_TYPES` (R61).
- P31: an env-gated test (`FERRITE_PG_EXPLAIN=1`) runs `EXPLAIN (ANALYZE, BUFFERS)` on the Postgres job claim over 50 000 future rows, 3 due and 2 expired leases; pass when rows read ≤ 10 × `LIMIT` + due rows, else split the claim into a `UNION ALL` of the due and expired-lease branches; the plan goes in the exit doc; an index would be a new ruling — cost: none. As built (Task 7): "rows read" is `Actual Rows` plus `Rows Removed by Filter`/`Index Recheck`, times loops (R53); the old claim read 50 005 rows, so the claim is now the `UNION ALL` split, which reads 12; no index (R54).
- P32: admin screen `/admin/import` (sidebar between Plugins and Settings, `can("import")`, chord `g i` if free in 11 §6): start card (WXR and zip drop zones, the four toggles, an Advanced disclosure for the bases, "Start import"), an active-run panel polling `GET /import/jobs/{id}` every 2 s while queued or running (stepper, heartbeat, counts, error), and a runs table with report links; XHR upload with progress and `Idempotency-Key`; every 11 §8 item; the route chunk fits the unchanged `largest_lazy` — cost: none.
- P33: `SeoSection` gains a canonical URL input and the five robots toggles (`noindex`, `nofollow`, `noarchive`, `nosnippet`, `noimageindex`), carried by `SeoDraft`, the autosave slot, the save patch and the 412 diff; "Reset to defaults" clears them — cost: none.
- P34: the M3 exit (`docs/superpowers/m3-exit.md`) records the UI import E2E on `chromium-sqlite` and `chromium-pg`, the full `e2e:all` matrix, the Docker cluster import through the API with a zipped uploads folder, every workspace gate on both backends and the P31 EXPLAIN output; anything not run is listed as not verified — cost: none.

## M3-2 execution rulings

Numbered in the order they were made (the controller's ledger), continuing M3-1's R51.

- R52: wave 1 runs Tasks 1, 3 and 6 as sessions and Tasks 7 and 8 as worktree subagents — at most three session cards per turn — cost: none.
- R53: P31's "rows read" is `Actual Rows` plus `Rows Removed by Filter`/`Index Recheck`, times loops — `Actual Rows` alone hides a filtered scan — cost: none.
- R54: no `run_at`-leading index now; the claim's due branch walks the index tuples of future jobs (about 0.5 ms at 50 000, index-only) — an M4 performance follow-up — cost: linear growth past about 500 000 future jobs.
- R55: the autosave omits an invalid canonical URL — a `422` would lose the whole draft — cost: a reload restores the stored canonical, not the half-typed text.
- R56: the expand lint accepts a same-name constraint swap only when the up and the down are both `CHECK (col IN (literals))` on the same column and the up's list is a strict superset — keeps 02 §8's guard — cost: other widenings must be marked contract.
- R57: `create_run` keeps `&ImportRun` (as built); `step` is free text in the store and core validates it — cost: none.
- R58: the uploads zip's end records (and the zip64 locator and record) are read first; over 500 000 declared entries or a central directory over 64 MiB is refused before `ZipArchive::new` — the parse would allocate first — cost: none.
- R59: `zip =9.1.3` with `features = ["deflate-flate2-zlib-rs"]` — `&self` entry access and tight central-directory preallocation, which 8.6.0 lacks — cost: freshness risk (published 2026-10-27).
- R60: `RunFailed.report` is `Option<Box<Report>>` (as built; clippy `result_large_err`) — cost: none.
- R61: each `permalink.redirects` page transaction takes `LOCK_TYPES` and re-reads the stored rules and kinds — concurrent jobs read stale rules otherwise — cost: the lock is held for a page of 500.
- R62: `permalink.redirects` pages by a published-order cursor (as built) — the store has no id order — cost: an item whose `published_at` moves later during the job gets no redirect (noted in 06).
- R63: imported posts may get redirects from never-live default paths — accepted under P30's cost, documented — cost: unused rows.
- R64: `enqueue` sets the payload's `user` to the actor in core; the request type has no user — cost: none.
- R65: `enqueue` first abandons a stale run; a run silent for over 120 s no longer blocks an admin's POST — an explicit request — cost: a CLI run paused over 120 s is abandoned (its fence then stops it).
- R66: the run reads return runs without their fencing token (`ImportRunView`) — cost: none.
- R67: the API's read-only conflict pre-check runs before the body is read (stale runs pass and are not abandoned there); the enqueue transaction's check is authoritative — cost: none.
- R68: an upload's stored-but-unrecorded blobs are deleted under `LOCK_IMPORT` (waiting at most 5 s), else left for the M4 orphan sweep — cost: rare orphan blobs until M4.
- R69 (P27 as built): a job's `start` takes over a stale run atomically when its `job_id` is none (a crashed CLI), its job is not `running`, or it is this job; a fresh run stays `Busy` — a foreign stale run blocked the job for ever — cost: a job whose lease expired still counts as live until it is reclaimed.
- R70: a `Retry` of the last attempt deletes the inputs; a lease that expires on the last attempt goes `dead` in the reaper, and those inputs leak until the M4 orphan sweep (accepted) — cost: orphan inputs until M4.
- R71: the dedup race between the job's input deletion and a new POST is not reachable — the enqueue transaction sees the job `running` throughout `delete_inputs` — cost: none.
- R72: the admin keeps the `Idempotency-Key` on a `5xx` and offers Retry; only `4xx` refusals other than the in-progress `409` rotate it — a proxy timeout must not start a second import — cost: none.
- R73: `system.spec`'s schema-version assertion derives the current version instead of a literal — cost: none.
- R74 (final review BE1): an import input's `artifacts` row is deleted first and its blob only when that succeeded — the media foreign keys refuse a row a media item still references (an upload of the same bytes keeps the `import` row), so the FK is the guard — reverses Task 4's blob-first order — cost: a failed row delete leaves the blob for the M4 sweep.
- R75 (final review BE2): `permalink.redirects` does at most 20 pages (10 000 items) per job, then enqueues a continuation with the cursor and the same previous and new values (`unique_key` `permalink.redirects:<version>:<cursor>`); the default timeout stays — a retry restarted at page 1, so a large site could go `dead` with partial redirects — cost: one job row per 10 000 items.
- R76 (final review BE-m1, accepted): a redirect written in a page transaction can shadow an item published at that old path concurrently — a narrow window, documented in 06 — cost: such an item 301s until the redirect is removed.
- R77 (final review BE-m2): the job and run reads report a stale `running` run whose job is `dead` as `abandoned` (read side only) — a run whose last attempt died showed "running" until the next import — cost: none.
- R78 (final review BE-m3): when a job's outcome is final and not `Ok`, its run's work folder `<data>/import/<run-id>/` is removed, and the job folder sweep also removes run folders whose run is not `running` — failed runs' IR folders were never removed — cost: a CLI re-run after a dead job cannot resume its IR.
